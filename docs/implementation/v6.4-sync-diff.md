# V6.4 资料包同步：差异清单与落地记录

资料包：`机动车检测预约_完整开发资料包_V6.4_第三方接入配置版`（上一版 V6.3）
分支：`rongli-wx`　执行日期：2026-10-23

## 0. 结论先说

V6.4 的实质增量只有一条主线：**PRD 新增第 23 章「第三方服务接入配置」，技术架构从 T3.3 升到 T3.4**。
它要解决的问题不是"再加几个配置项"，而是把支付/短信/订阅这类**有外部副作用**的能力，从"改配置文件重启"变成
"后台草稿→校验→发布"，并且保证：**发布出去的版本可追溯、凭据只写不读、能力未配置时宁可拒绝也不静默降级**。

本次已完成（可重跑验证）：

- 数据层：12 张新表 + 支付表 9 列 + 退款表 2 列 + 19 条菜单 + 5 个业务参数，迁移可重复执行
- 后端：35 个新端点（后台 27 + 线下资金 4 + 车主支付方式 2 + 订阅授权 2），编译与启动通过
- 后台：B46–B53 八个页面 + 两个通用组件，前端构建通过
- 小程序：支付方式由服务端下发（微信/线下双开关）、线下付款意向、订阅授权上报

第二轮（身份域收口 + 自动下发，见第 5 节）：

- 数据层：3 个迁移把身份域 13 个列补齐、2 张退役表彻底删除、31 条孤儿支付单清理并建齐 3 个支付约束；
  `vi_*` 从 82 张收敛到 **80 张**（= V6.4 的 79 张 + 本库保留的 `vi_sms_send_log`）
- 后端：V6.4 身份流程落地（微信手机号唯一匹配自动关联、跨账号冲突拒绝并留痕、短信兜底不再作为关联依据）；
  `NotificationDispatchService` 接通「业务事件 → 路由 → 模板 → 投递」全链路
- 验收：**327 条断言全通过（100%，0 跳过）**，新增 `SND` 消息自动下发套件

已无阻塞项。真实收款/真实送达仍需凭据（见 5.5），那是外部条件不是代码缺口。

### 5.1 身份域 13 个列 —— 已加列，历史行标记为 `MANUAL_LEGACY`

| 表 | 新增列 | 说明 |
|---|---|---|
| `vi_account` | `phone_verified_at`、`phone_source`、`employee_auto_link_blocked` | `phone_source` 受 `ck_account_phone_source` 约束（WECHAT / SMS） |

当初卡住的点：`phone_lookup` / `last_phone_verified_at` / `employee_auth_version` 在资料包里是 NOT NULL，

界面上对外仍报 `employeeBindSource=CREDENTIAL`（仅 `MANUAL_LEGACY` 行），保持既有契约不破。

```sql
CONSTRAINT `ck_ver_driver_statement_membership_change` CHECK (`version` >= 0)
```

但 `vi_driver_statement_membership_change` **没有 `version` 列**（实际 11 列：id / statement_id / ledger_id / line_id /
action / revision_before / revision_after / actor_user_id / reason / snapshot_json / created_at）。
照抄执行的后果比"报个错"严重：`ERROR 3820 Check constraint ... refers to non-existing column 'version'`
发生在第 1256 行，**整份脚本从这里中断——79 张表只建成 56 张，后面 23 张全缺**（已实测）。
（对已有表 ALTER 时是另一个报法：`ERROR 1054 Unknown column 'version'`。）

**这是上游的笔误，不是本库缺列。** 原因是这张表的性质：它是"对账成员变更**不可变历史**"，
只追加、永不 UPDATE，本来就不做乐观锁，所以没有 `version` 列是对的——
上游那套 `ck_ver_<表名>` 约束是按"所有业务表都有 version"批量生成的，到这张表就落空了。

修法上有个岔路口，两个选项我选了后者：

| 方案 | 后果 |
|---|---|
| 给表加一个 `version` 列满足约束 | 一张只追加的表加乐观锁列，值永远是 0，语义名存实亡，还改了资料包的结构 |
| **把"版本不得为负"校验到真实存在的版本列上** | 约束照常生效，结构的表意也保住了 |

最终落地（`migration_20261023_04` 第三节，幂等）：

```sql
ALTER TABLE `vi_driver_statement_membership_change`
  ADD CONSTRAINT `ck_ver_driver_statement_membership_change`
  CHECK (`revision_before` >= 0 AND `revision_after` >= 0)
```

三个细节：

- **约束名沿用上游原名**，这样与资料包逐表比对时不会出现"少一条约束"的假差异
- 验收里加了 `S6c` 断言，同时校验"约束存在"与"表里确实没有 `version` 列"——
  防止以后有人为了对齐资料包，偷偷给这张表加上一个永远为 0 的 version 列
- **资料包已就地修正**：`机动车检测预约_完整开发资料包_V6.4_第三方接入配置版.zip` 内的
  `05_数据设计/001_vi业务表_初始化_V6.4.sql` 那一行已替换（原包备份为同目录 `.bak-20261023`）。
  修正后整份 SQL 灌空库建成 **79 张表**；修正前在第 1256 行中断，只建成 **56 张**

实测：负数版本 → `ERROR 3819 Check constraint ... is violated`；正常版本 → 可写；回滚无残留。
迁移连跑两次均 `statement_change_ver_ck=1`。

### 5.5 真实联调凭据 —— 唯一剩下的外部条件

以下都缺，导致 `LIVE` 只能做到"拒绝得清楚"，做不到"能收钱/能送达"。这些不是代码缺口，是账号物料：

| 配置 | 缺什么 | 影响 |
|---|---|---|
| B47 微信支付 | 商户号、商户证书序列号、商户签名私钥、APIv3 密钥、微信支付公钥 | 无法真实收款 |
| B53 小程序公共凭据 | AppID / AppSecret | 订阅消息与 JSAPI 都依赖它 |
| B48 短信通道 | 腾讯云 SecretId/SecretKey/SdkAppId/签名，或阿里云 AccessKey/签名 | 短信发不出，只能发站内消息 |
| B49/B50 模板 | 供应商已审核的模板 ID | 模板未发布时该场景发送会被明确拒绝（不会静默漏发） |
| 部署环境变量 | `VI_INTEGRATION_MASTER_KEY` | 未配置时根密钥回落到部署数据密钥，校验会给 `VI_CONFIG_KEY_SOURCE` 警告，生产必须配 |

拿到物料后按这个顺序配：B53 小程序凭据 → B48 短信通道 → B47 微信支付 → B49/B50 模板 →
最后用 B51 的联调白名单做一次真实发送（白名单限制是"只有白名单手机号能收到真实短信"，不是"只有白名单能触发"）。

### 5.6 仍剩一件小事：小程序订阅授权的时机

支付页已接订阅授权入口，订单详情页/交接页的授权时机还没加。

订阅是"一次授权一次推送"的：用户在支付页点了允许，只对该模板的**一次**推送有效。所以下单成功、
派单成功、检测完成这些时点，都需要在下一次相关操作前重新取一次授权。当前只有支付页有入口，
意味着"派单成功"这类推送大概率因未订阅而 `SKIPPED`（记录里是 `VI_NOTIF_USER_UNSUBSCRIBED`，不是失败）。

不影响站内消息送达，属于体验优化，不阻塞上线。
