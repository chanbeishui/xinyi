## 复核范围与已处理发现

复核覆盖退款 Controller、DTO、`RefundExecutionService`、`WechatRefundGateway`、`RefundSettlementService`、`RefundExecutionJob/Dispatcher`、永久对账及操作原因服务、MyBatis XML、新资金认证链，并检查原支付历史查询/通知接入点、严格 404 验签运输层、迁移及主 PRD/B31 操作规格。前端构建和浏览器运行证据由主任务单列，本文件仅核对资金动作、原号、版本和单次审核的调用边界。

1. **既有渠道退款号不能被覆盖。** PROCESSING 已有 `channel_refund_id` 时，后续事实原先可能用不同渠道 ID 覆盖。已补所有已知渠道 ID 与新事实的匹配校验；与原退款号、商户交易号、交易 ID、原总额、退款额、币种及可信成功时间一起约束落账。渠道 ID 按不透明字符串处理，测试使用超过 Long 的真实形状 ID。
2. **外部 IO 后再发 POST 须重新校验。** 原支付预查可能等待数秒，已拆为事务外 preflight、短事务内当前身份/资金范围/租约/生效审核版本/实物条件校验，再事务外提交原参。预查期间撤权能立即落库，并阻止追加新的退款 POST。已经实际发生的可信渠道资金事实仍可归并，最终用户读取再次鉴权；不会以会话撤销为理由抹去真实已退事实。
3. **SDK 非 2xx 的 404 不能直接当证据。** 默认 SDK 会在常规响应 validator 前抛非 2xx ServiceException，专用退款运输层已对唯一签名头、响应体大小及官方 validator 做额外校验。只有已验签的 `404/RESOURCE_NOT_EXISTS` 且当前人工授权、租约、审核和实物条件仍有效，才允许原号原参数受控再次 POST；无签名、坏签名、未知结果或 CLOSED 不得触发此动作。自动任务查无结果不自动重提。
4. **操作原因原先只有 MAC，现加密留存。** 退款人工查询/重试和对账重查/办结的必填 reason 原先只参与幂等摘要，无法追溯实际说明。现复用版本化 AES-GCM，将说明按 `P04:ADMIN:{userId}:{action}:{recordId}` 绑定后写成功意图审计的 `reasonEnvelope`；审计正文保留固定脱敏说明，不在 GET、outbox、幂等结果或失败日志回显原文。首次成功意图同事务记录一次，重放不新增密文；无密钥不能降级明文。独立新增回归已实际验证四类动作、正确解密、错动作/记录拒解及明文不泄露。
5. **首轮测试夹具问题已纠正。** 父子 DynamicPropertySource 对同键注册顺序使退款测试请求误入旧支付替身；P04 已用仅测试上下文的静态 BeanFactoryPostProcessor 固定独立回环端口，并在每例断言实际 Environment 端口。没有改变生产 endpoint 或放宽原支付身份校验。并发回调改为同一事件的完全相同原文重投；原文冲突仍拒绝。并发工作器经过真实 job，合法 busy 租约拒绝由工作器留痕，未取消底层 CAS。旧 P02 回调夹具补齐对应申请和同版批准记录，原资金断言保持。

## 资金、并发及权限判断

- S02 已批准且与原订单、支付、同版决定及金额对应的退款单才可执行；客户端仅提交版本和操作说明，不能覆盖金额、商户、收款主体、渠道、case 或退款号。金额使用整数分，成功或可信 CLOSED 在同一支付锁内消费预留；SUCCESS 才增加已退。终态和已知渠道 ID 不允许晚到响应覆盖。
- 新发起前持久化意图及 60 秒数据库租约，IO 不持业务长事务；提交、查询与回调共享一个落账服务。租约和版本隔离旧执行者，崩溃恢复先查原号，不依赖 Redis 或进程内定时器。固定原号、原金额、原商户身份及永久业务唯一键防止重复业务退款，传输不自动重试或跟随重定向。
- 本次原支付查询核对真实 merchant/app/transaction/金额；历史开关关闭不改变旧资金身份，同商户有效凭据轮换继续使用。官方退款响应不额外伪造 mchid 字段；商户以已验证请求配置和真实回调 mchid 约束。
- 未实际归还的取消审批不主动发渠道，也不释放司机/容量；0 元没有退款单。可信真实退款若提前到达，仅如实记资金，保留待返还、实际保管及司机占用，不能据此伪造还车。仅退款不改履约和承接。OFFLINE 查询仅读本地待凭证状态，不调用微信，不因重试执行人工付款。
- 六个资金接口只接受真实 ADMIN 凭据，认证失败真实 HTTP 401。功能权限与原支付 receiver_dept_id 数据范围同时执行，空范围 fail-closed；订单站点部门不能代替收款公司。旧 auth_version 在缓存删除故障下仍失效。数据归属、余额、版本、当前会话及成功/拒绝审计均由服务端执行。
- 数据库约束和 outbox 故障覆盖资金、退款状态、成功审计、事件去重的事务回滚。渠道未知保留原预留和原号；ABNORMAL 保留预留并转异常，人工受控重试仍先查原号。CLOSED 为可信终态，释放旧预留但保留异常处置，不自动换号。

## 对账、规范与 SQL

对账为独立永久 `vi_payment_reconciliation`，PAYMENT/REFUND 各自解释 subject_id，并以两者联合唯一键防重复；异常可重开，不删除旧审计。查询可信渠道与人工登记办结分开。办结须已核对的终态、当前本地状态、支付余额与退款明细账以及相关容量事实一致，文字说明本身不改资金或把未知变成功。

已核对主 PRD 5.6 与 B31 页面规格：动作是按原号查询、可信未受理后的原参重试、重查异常、核实一致后登记办结；没有第二次批准退款，也不手工改付款/退款状态。实际 UI 对应 query/retry/resolve，无另设审批入口。

迁移 `migration_20261107_01_refund_execution.sql` 同步完整初始化，并包含历史执行意图的保守回填、异常记录、稳定菜单、异常查询与重启/备份说明。主任务 schema-verification 已记录两表的字段类型、默认值、注释、生成表达式、约束/索引及 6 条权限菜单一致，历史原号未变、未改业务/生产库。旧库 `payment_method/execution_mode` 只存在历史列序差异，比较按名称与结构含义进行，没有为列序重写历史交易。
