# P04 退款执行与支付对账交付

S02已批准的稳定退款单现已接入官方微信支付SDK、执行任务、可信查询/通知归并和持久支付/退款对账。PC新增“渠道退款”和“支付对账异常”，售后批准记录可按原退款号进入详情。六个接口均有真实Controller、Service、MyBatis及HTTP/MySQL验证，不新增第二次退款审核。

| 场景 | 执行及资金结果 |
|---|---|
| 首次已批准可执行退款 | 持久化提交意图/租约，核实原付款，再按原商户、原号、原金额请求 |
| 超时、断网、验签/身份/金额失败 | UNKNOWN并保留预留；后续先查原退款号 |
| 可信未受理 | 仅签名有效的RESOURCE_NOT_EXISTS允许人工明确原号原参重试；没有签名的404不授权重提 |
| PROCESSING / ABNORMAL | 受理不当成功；保留预留，原号核查，异常进入永久对账 |
| SUCCESS | 统一落账一次，消费对应预留并增加实退，重复通知/查询不重复计账 |
| CLOSED | 可信终态释放原预留，保留ABNORMAL待处理；原号禁止重提，不能自动换号 |
| WAIT_RETURN | 真实归还前不主动退款；可信已发生退款仍如实入账，实物保管/司机承接保持原事实 |
| OFFLINE | 退款详情查询本地进度，不调微信；重试422，实际凭证核实由X06完成 |

## 权限、事务与审计

退款与对账资金范围均从原支付`receiver_dept_id`校验，不能用站点订单部门、用户主部门或客户端字段代替。ADMIN功能权限与部门范围分别校验，空范围关闭。资金端点无登录、MINI Token或伪造realm返回真实HTTP401；旧`auth_version`即使Redis删除失败也失效。新增菜单不自动授予角色。

目录/后台授权、原订单、原支付、售后、退款/对账按统一顺序加锁；执行租约、重试退避和CAS持久化。网络调用在事务外，原付款预检之后、退款POST之前重读授权、审批版本、实物条件与租约。可信资金落账重新核对原单审批证据及执行租约，不因操作者刚撤权或尚未归还而丢弃真实已退事实；返回操作者结果前再次鉴权。进程在提交后退出时，下次只查原号；内部工作器正常租约竞争无副作用退出，后台人工冲突仍409。关闭新微信支付开关不阻历史原商户交易的查单、退款和验签，轮换凭据仍匹配原身份。

回调、查询和提交回执共用`RefundSettlementService`：校验原交易、批准版本/金额、币种、不透明渠道退款号及可信成功时间，余额、状态、审计与outbox同事务。数据库或outbox失败整笔回滚。退款结果不写司机占用，不把到账当作归还。

人工查询/重试/办结绑定版本、500字以内原因与UUID幂等键。操作原因使用已有AES-GCM密钥体系加密留存，AAD绑定ADMIN、动作与真实记录ID；审计只写受控说明和加密封装，GET/outbox/幂等结果不含原文。同键同体只留一次，异体拒绝；缺密钥不降级明文。密钥历史版本必须保留，授权审计流程才能解密。

永久对账记录按`kind+subject_id`唯一，可重开并保留审计。重查可信渠道与登记办结分开；本地/渠道终态、预留/实退台账及容量事实不一致时不能办结，文字原因不能手工认账。支付成功但容量仍MANUAL_CONFLICT时也不能用对账按钮消除履约冲突。
