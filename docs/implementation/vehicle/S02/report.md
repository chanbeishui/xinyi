# S02 一次审核及退款预留交付

后台“取消与退款”现支持列表筛选、订单/车主范围记录、代办申请、公开补充凭证、实时结果预览及一次批准/驳回。八个接口已接入真实 Controller、Service、MyBatis；订单及车主详情可跳转同一页面。

| 情形 | 审核后事实 | 资金与资源 |
|---|---|---|
| 未接车取消获批 | 正式取消，保留旧任务历史 | 精确撤销对应邀约/承接，释放未用额度；正金额预留并建稳定退款单，0元不建单 |
| 已接车且未实际归还 | 取消已通过、等待返还，原履约与保管保留 | 批准款预留，司机继续承接；0元仍须真实返还 |
| 仅退款获批 | 保持履约与保管 | 按同一次决定预留，不释放司机；有完整审核证据的余额不阻后续预约派单 |
| 驳回 | 售后及审核历史保留驳回，撤销本次取消意图 | 不新增预留，不回滚实际交接、保管或履约 |

业务范围来自原订单 `dept_id`，资金查看/批准分别要求 `biz:refund:query`、`biz:refund:approve` 及原支付 `receiver_dept_id` 范围。只有协助取消功能不能预留退款。列表/详情无资金查看范围时金额为null；新增权限不自动分配给旧角色。后台代办页面先通过既有订单查询核对版本，需要 `biz:order:query`；凭证另需F01文件权限。

申请、补充资料和受益车主的可信同人关系均参与独立审核排除。MINI账户与ADMIN用户不数值混比；历史绑定、已核验手机号与冻结的追加关系可防止通过解绑、换号或切换身份自审。内部 `opinion` 和车主可见 `publicOpinion` 分别保存；旧内部意见不猜测为公开说明。后台公开补充的凭证仅在明确关联原订单售后历史后，允许该车主读取；上传草稿不会自动公开。

预览明确 `APPROVE/REJECT`，省略兼容旧客户端按APPROVE。驳回只接受0元且不预览返还/预留动作；批准仅退款必须正金额。预览绑定UUID幂等键与内容，只缓存申请ID，重复请求仍实时检查权限、版本、保管和余额，不缓存旧资金快照。最终决定同时检查申请/订单两个版本；409保留填写意见，刷新并重新预览，未知结果保持原请求及幂等键。

审核在目录/用户、原订单、支付、申请及资源锁内提交决定、余额预留、退款单、审计与outbox；失败全部回滚。退款号由申请及审核版本永久确定，采用原支付方式和执行模式，当前支付开关不改写历史路由。提前结束承接同时登记永久幂等 `ASSIGNMENT_ENDED:{id}` 事件，供后续费用任务使用，不在本任务计算报酬。P03仅在合法仅退款记录能完整解释预留/已退金额时继续派单；无法解释的余额仍转人工。
