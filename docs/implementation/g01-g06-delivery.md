# G01~G06 交付说明

本轮交付 6 项：三项外部通道配置（支付/短信/订阅）、站内交接双方确认、手机号唯一校验、
售后申诉对账端到端回归。所有结论都有可重跑的证据命令，见文末。

## 二、三个配置页在哪、怎么用

菜单路径：**系统设置 → 业务参数 / 微信支付 / 短信通道 / 订阅消息**
权限标识：`biz:config:param`、`biz:config:payment`、`biz:config:sms`、`biz:config:subscribe`

每页统一有三块：当前状态徽标（`MOCK` / `INCOMPLETE` / `INVALID` / `READY`）、
缺失项清单、字段说明（取自后端 `fieldMeta`，与实际校验规则同源，不会出现
"页面说选填、后端当必填"的错位）。

敏感项（APIv3 密钥、商户私钥、平台证书、AccessKeySecret、SecretKey、AppSecret）
只回显"是否已配置 + 末 4 位掩码"，保存时提交 `__UNCHANGED__` 表示保持原值，
提交空串表示清空——避免"打开页面直接保存"把密钥抹掉。

### 2.1 微信支付（G01）

| 字段 | 必填 | 校验规则 | 取值位置 |
|---|---|---|---|
| 支付通道 | 是 | `MOCK` / `WECHAT` | 联调选 MOCK，上线切 WECHAT |
| 小程序 AppID | 切 WECHAT 后必填 | `^wx[0-9a-fA-F]{16}$` | 微信公众平台 → 开发管理 → 开发设置 |
| 商户号 | 同上 | `^\d{8,12}$` | 商户平台 → 账户中心 → 商户信息 |
| APIv3 密钥 | 同上 | 32 位字母数字 | 商户平台 → API安全 → 设置 APIv3 密钥 |
| 商户证书序列号 | 同上 | 十六进制 16~64 位 | 商户平台 → API安全 → 申请 API 证书 |
| 商户私钥 | 同上 | 必须能解析为合法 PKCS#8 PEM | 下载的 `apiclient_key.pem` 全文 |
| 平台证书序列号 | 否 | 十六进制 16~64 位 | 用于回调验签 |
| 平台证书 | 开启验签且真实通道时必填 | 合法 X.509 PEM | 微信支付公钥 / 平台证书 |
| 支付回调地址 | 切 WECHAT 后必填 | 必须 https | `https://你的域名/api/common/pay/notify` |
| 退款回调地址 | 否 | https；留空自动取支付回调并替换末段 | — |
| 商品描述 | 是 | 1~127 字符 | 用户在支付弹窗看到的那句话 |

规则要点：

- **必填与否取决于通道，但"填了就必须填对"与通道无关**。联调期填 `wx123` 也会被拒，
  否则错误值会一直躺在配置里，等切真实通道那天才在支付瞬间炸掉。
- 联调通道（`MOCK`）不要求平台证书：这个通道的通知由服务端自己构造明文，根本不验签。
- 保存前会先跑一次本地签名自检（`POST /api/admin/config/payment/self-check`），
  私钥与签名串对不上会当场报出来，不用等真实下单。
- 配置不全时下单不会静默失败：`prepay` 直接返回 `503 CHANNEL_UNAVAILABLE` 并列出缺哪几项。

### 2.2 短信通道（G02）

| 字段 | 必填 | 校验规则 |
|---|---|---|
| 启用短信 | 是 | 布尔；关闭时验证码走联调回显，不调供应商 |
| 供应商 | 是 | `ALIYUN` / `TENCENT` |
| 短信签名 | 开启后必填 | 2~20 字符 |
| 短信模板编号 | 开启后必填 | 供应商侧模板 CODE |
| AccessKeyId / AccessKeySecret | 阿里云必填 | 密钥为敏感项 |
| SecretId / SecretKey / SdkAppId / Region | 腾讯云必填 | Region 默认 `ap-guangzhou` |
| 验证码有效期 | 是 | 60~1800 秒（默认 300） |
| 重发间隔 | 是 | 10~600 秒（默认 60） |
| 单号日上限 | 是 | 1~50 条（默认 10） |

频控三层，全部命中才真正下发：

1. **重发间隔**：同一手机号距上次成功发送不足间隔秒数直接拒；
2. **手机号日上限**：同一号码当日条数达上限拒；
3. **账号日上限**：同一账号当日条数达上限拒。

被限流的请求也会写 `vi_sms_send_log` 并标 `BLOCKED`，与"供应商返回失败"分开记，
免得运营把限流当成通道故障去排查。发送结果中文化：`isv.MOBILE_NUMBER_ILLEGAL`
→「手机号格式不正确」，`isv.BUSINESS_LIMIT_CONTROL` →「发送过于频繁」。

页面上有「发送测试短信」按钮，填一个手机号即可验证凭据与签名是否配对，
测试记录同样落日志，便于事后核对。

### 2.3 订阅消息（G03）

| 字段 | 必填 | 校验规则 |
|---|---|---|
| 启用订阅消息 | 是 | 关闭时只发站内信 |
| 派单邀约 / 接单成功 / 结果可查看 / 退款完成 模板 ID | 至少一个场景 | `^[A-Za-z0-9_-]{10,64}$` |
| 点击跳转页面 | 是 | 不以 `/` 开头、不含空格，如 `pages/order/detail` |
| 运行环境 | 是 | `developer` / `trial` / `formal` |
| 字段映射 | 是 | JSON：模板字段名 → 取值来源（`content` / `now` / `scene`）；字段名形如 `thing1`、`time2` |
| 小程序 AppID | 启用时必填 | `^wx[0-9a-fA-F]{16}$`，与登录共用 |
| 小程序 AppSecret | 启用时必填 | 敏感项，与登录共用 |

规则要点：

- **"填错了"拒绝保存，"还没填"允许保存**。格式类问题（模板 ID 格式、页面路径、
  运行环境、字段映射 JSON）必须当场改对；必填项缺失只提示、不拦保存，
  返回 `status: INCOMPLETE` 并用一句话列出还差什么。
  这样运营可以先关开关、慢慢配，而不会被必填项永久锁死在关闭状态。
- 缺模板时整条链路只是"多写一条站内信"，运营会误以为已推到微信，所以状态会明确标
  `INCOMPLETE` 而不是装作正常。
- 自检会真实换一次 `access_token`，这是唯一能证明 AppID/AppSecret 配对且未过期的本地手段。

## 三、G04 站内交接双方确认

### 改了什么

站内交接（`DRIVER_TO_STATION`，可配：`rongli.handover.mutualConfirmTypes`）此前
只要核验方输入交接码就直接完成，司机侧没有"我把车交出去了"这个动作。现在改成两段：

```
检测员工发起交接
   ↓  司机出示 4 位交接码
检测员工输码确认（核验方）  →  status = PARTIAL，记 verifier_confirmed_at
   ↓  司机在自己端内点「确认已交付」（持码方，无需再输码）
司机确认                  →  status = CONFIRMED，记 holder_confirmed_at
   ↓
订单推进到下一状态
```

关键实现点：

- 只有 `CONFIRMED` 才推进订单；`PARTIAL` 阶段订单停在原地，并给持码方与车主各推一条
  提醒，事件日志留 `HANDOVER_HALF_CONFIRMED`。
- 唯一性没有放开：`vi_handover.active_key` 是 STORED 生成列 + 唯一索引，
  表达式从 `status='PENDING'` 扩为 `IN ('PENDING','PARTIAL')`，
  保证半确认期间同一订单不会再生出第二条有效交接。
- 两端确认都有防重：`verifier_confirmed_at IS NULL` / `holder_confirmed_at IS NULL` 做条件更新。
- 后台代客确认时如果停在 `PARTIAL`，会自动补齐持码方确认，并留 `holderConfirmedByAdmin` 痕迹。

### 怎么用

小程序「代驾 → 我的任务」：车辆交接卡片在 `canCounterConfirm` 为真时出现
**「确认已交付」**按钮；点完交接状态从「待对方确认」变为「已完成」，订单随即推进。
检测员工侧不变：输 4 位码确认收车。

## 四、G05 手机号唯一校验

- `sys_user` 增加生成列 `phone_unique`：仅当 `del_flag='0'` 且手机号非空时取值，
  配合唯一索引 `uk_sys_user_phone`。这样**软删除的账号不占用手机号**，
  空手机号也不会互相冲突。
- 新增 / 编辑 / 注册三个入口都做了冲突翻译：捕获 `DuplicateKeyException` 且消息含
  `uk_sys_user_phone` 时，转成可操作的提示——「该手机号已被其他账号使用，
  请核对是否重复录入；若为历史重复数据，请先修正原账号手机号」，
  而不是把数据库唯一键错误直接抛给用户。
- 历史重复数据不会被这次迁移"清理"，迁移只加约束；若库里已有重复手机号，
  约束会建不上，需要先人工合并——这是有意的，避免自动删数据。

## 五、G06 售后 / 申诉 / 对账端到端

`logs/verify_aftersale_flow.py` 覆盖三条此前只做过接口冒烟的链路，重点是"状态真的走完了"：

1. **售后**：下单 → 支付 → 车主发起取消退款 → 后台列表可见 → 审核预览可退金额 →
   审核通过 → 断言「售后单 `CLOSED`」「订单 `CANCELLED`」「退款 `SUCCESS`」
   「退款金额与申请一致」→ 退款单详情 → 主动查退款。
2. **申诉**：建代驾档案 → 切视角 → 落一条罚款 → 代驾端可见 → 提交申诉 →
   后台审核通过 → 断言处罚 `REVOKED`。
3. **对账**：落一条对账异常单 → 列表可见 → 发起渠道重查（`CHECKING`）→
   登记结论 → 断言 `RESOLVED`。

脚本自带前后清理，可反复运行。

## 六、顺带修掉的三个真实缺陷

这三个都是做上面功能时被测试逼出来的，不是顺手重构：

1. **小程序业务错误一律返回 HTTP 200**。框架的 `GlobalExceptionHandler` 优先级高于
   荣利的 `ViExceptionHandler`，把所有异常都包成 `HTTP 200 + {code:500,msg}`。
   后果是客户端拿不到 401/403/409/422，令牌过期也不会触发自动续期，
   验收里 11 条断言因此全红。已给 `ViExceptionHandler` 加最高优先级，
   错误体同时带 `message` 与 `msg` 两个键（小程序读前者、后台读后者）。
2. **售后创建返回了管理端视图**。车主提交售后后，代码用 `detail(caseId, true)` 组装响应，
   走的是部门权限校验，小程序会话没有后台用户上下文，于是数据已入库但接口回 401，
   车主看到失败、重试又提示"已有处理中的申请"。已按申请人身份选择视图口径。
3. **订阅配置一关就再也开不回来**。必填缺失被当作硬错误拦截保存，
   运营关掉开关后就永远无法重新开启。已拆成"格式错误拦截 / 必填缺失提示"两类。
