时间范围：2026-11-04 ~ 2026-11-09。目标是把「从零到上线」这条路上踩过的坑，判断哪些该固化成可复用资产，
哪些只是本项目的一次性事件。

期间修掉的、**不看就会再踩**的问题（按出现顺序）：

1. `application-druid.yml` 的 profile 顺序（必须 `druid,prod`，写反连回开发库）
2. 基础 SQL 不含 `QRTZ_*`，`quartz.sql` 必须单独导
3. 迁移脚本硬编码 `USE xinyi` / `TABLE_SCHEMA='xinyi'`，换库名即中断
4. MySQL 容器 `my.cnf` 参数写进 `[client]` 段不生效；`lower_case_table_names` 不可改
5. 容器默认 UTC，缺 `default-time-zone` 会差 8 小时
6. 未装 JDK → systemd `203/EXEC` 无限重启
7. `/home/xinyi` 750 → nginx 403
8. 前端包上传 403/白屏的三种成因（权限、多套一层目录、index 缓存）
9. Actions 里 `scp` 用 `-p` 指定端口（应为 `-P`），报 `stat local "22"`
10. Secret 值带空格/换行 → 远端目标被当成本地路径，报错表现同上

## 二、评估维度

对每个候选用四个维度衡量，避免"什么都想做成 skill"：

- **复用频率**：换一个项目还会不会遇到（高=几乎每个项目都要做）
- **踩坑密度**：不查资料/不提醒会不会做错（高=错了很难自查）
- **可脚本化**：能否变成确定性脚本或可执行清单（高=不依赖模型判断）
- **业务耦合**：与本项目业务逻辑绑定的程度（低=越通用）

## 三、分级清单

### 优先沉淀（3 项）

#### 1）`atomic-remote-deploy` — 原子远程部署与回滚

| 维度 | 评价 |
|---|---|
| 复用频率 | 高：任何"本机构建 → 传到服务器 → 重启服务"的项目 |
| 踩坑密度 | 高：半截切换、健康检查缺失、失败无回滚、scp 参数坑 |
| 可脚本化 | 高：`remote-deploy.sh` 已是成品，可直接抽成模板 |
| 业务耦合 | 低：只依赖服务名与目录约定 |

- **适用场景**：Spring Boot / Node / Go 单机部署；需要"发布失败自动退回上一版"；CI 与本机共用同一套部署逻辑。
- **核心流程**：产物上传到暂存目录 → 备份旧产物 → 原子切换 → 重启 → 轮询健康检查 → 失败自动回滚 → 写部署记录（commit/时间/操作人）。
- **关键注意**：先后端后前端（后端不健康就不动前端）；前端切换用 `mv` 而非原地覆盖；健康检查要打业务无关接口；`scp` 用 `-P`、`ssh` 用 `-p`；Secret 值必须去空白。
- **预期产出**：`remote-deploy.sh`（服务器端）、`deploy.sh`（本机一键）、GitHub Actions 工作流模板、回滚速查表。

#### 2）`linux-server-provisioning` — Linux 服务器上线底座

| 维度 | 评价 |
|---|---|
| 复用频率 | 高：每个新环境一次，且每次都从零 |
| 踩坑密度 | 极高：上表 10 个问题里 7 个属于这一环 |
| 可脚本化 | 中高：初始化可脚本化，取值判断需人确认 |
| 业务耦合 | 低：与具体业务无关，只与中间件有关 |

- **适用场景**：给 Spring Boot 类项目准备 Linux 生产环境（裸机或 1panel 托管 MySQL/Redis）；把已有项目迁到新服务器。
- **核心流程**：系统基线（时区/swap/更新）→ 中间件（容器化 MySQL/Redis，含 my.cnf 与内存上限）→ 建库建账号 → 按序导 SQL 并做结构断言 → 建运行用户与目录 → 生成 `.env` 与 `application-prod.yml` → 装 systemd 单元 → 探活。
- **关键注意**：库必须是 MySQL 8（`utf8mb4_0900_ai_ci`）；`quartz.sql` 单独导；skip demo seed；容器时区与连接串时区一致；家目录要给 `751` 否则 nginx 403；JDK 必须在装服务前装好。
- **预期产出**：`server-bootstrap.sh`（9 步、可重复执行、失败即停）、生产配置模板、systemd 模板、nginx 站点模板、排障对照表。

#### 3）`sql-migration-audit` — 迁移脚本可移植性与幂等审计

| 维度 | 评价 |
|---|---|
| 复用频率 | 高：任何带 `sql/migration_*.sql` 的项目 |
| 踩坑密度 | 高：换库名/重跑才暴露，本地因为"恰好同名"永远不报错 |
| 可脚本化 | 极高：纯静态分析，输入仓库、输出报告 |
| 业务耦合 | 无 |

- **适用场景**：评审新增迁移脚本；换库名/换环境前预检；CI 里作为 `sql-check` 的前置。
- **核心流程**：解析基础脚本得到表→列与表清单 → 扫描迁移脚本里的 `USE`、硬编码 schema、`ADD COLUMN`、`CREATE TABLE`、`ADD INDEX` → 与基础脚本比对，标出"不该失败却会失败"的位置 → 输出报告（文件/行/类型/建议改法）。
- **关键注意**：判断依据是"守卫条件能否在目标库生效"，不是"有没有写守卫"；`TABLE_SCHEMA='xinyi'` 这类**看似有守卫实则失效**的要单独标；同时检查 CI 用的库名是否与生产一致（一致会让问题永远隐形）。
- **预期产出**：审计脚本（Python）+ 报告模板 + CI 集成片段。

### 可选沉淀（3 项）

#### 4）`miniprogram-ci-release` — 小程序构建与上传

- **适用场景**：uni-app / 原生微信小程序需要"一键构建+上传"，且不想每次手点开发者工具。
- **核心流程**：读 manifest 取 appid → 校验产物与上传密钥 → `miniprogram-ci upload` → 输出后续人工步骤（设体验版/提审/发布）。
- **关键注意**：上传密钥 + 出口 IP 白名单是硬约束（不适合放 Actions）；上传后仍是开发版；备案未完成不能发布；版本号需单调递增。
- **预期产出**：`upload-mp.mjs` + npm scripts + 平台侧操作清单。
- **暂列可选的理由**：只对小程序项目有效；自动化边界只到"上传"，收益有限但重复劳动明确。

#### 5）`remote-debug-channels` — 联调通道选择

- **适用场景**：前端/移动端要对着"线上后端"开发；手机上要看本机正在改的版本。
- **核心流程**：四条通道按耗时排序（本地全栈 / 本地前端+远程后端 / 一键发布 / SSH 反向隧道），按场景选一条。
- **关键注意**：反向隧道用完必须关并注释 nginx 段；token 密钥不可在调试期改动；生产库不当测试池。
- **预期产出**：通道对照表 + 隧道与代理的可复制配置。
- **暂列可选的理由**：内容偏方法论，稳定后可并入 skill 2 的 reference。

#### 6）`oss-upload-troubleshooting` — 对象存储上传排障

- **适用场景**：图片/附件上传报 `找不到存储平台`、`AccessDenied`、图片裂图。
- **核心流程**：确认凭据是否注入（环境变量/配置中心）→ 平台是否注册 → RAM 是否含 `PutObjectAcl` → 桶是否关闭"阻止公共访问" → endpoint 是否公网 → CORS/同源兼容层。
- **关键注意**：普通上传正常但头像失败 = 缺 `oss:PutObjectAcl`；上传成功但手机端全白 = 用了 `-internal` endpoint；直链在 canvas 里失败 = 缺 CORS，应走同源兼容层。
- **预期产出**：症状→原因对照表 + 配置检查清单。
- **暂列可选的理由**：坑很硬但只出现在用 OSS 的项目；可与 skill 2 合并为"中间件排障"。

### 暂不建议沉淀（4 项）

| 内容 | 理由 |
|---|---|
| Windows ↔ Linux 操作混淆（窗口识别、`type` vs `cat`、粘贴乱码） | 属于通用环境 FAQ，写进 skill 2 的 troubleshooting 一节即可，单独成 skill 会被反复触发 |
| 本项目业务编排（荣利菜单/权限/身份流程） | 与业务强耦合，已作为仓库文档与迁移脚本存在，做成 skill 会随业务变更腐化 |
| 1panel 安装本身（一条 curl 脚本） | 无沉淀价值；有价值的是"装完必须做的加固"，已并入 skill 2 |
| 单次环境事故（产品名被替换成随机串） | 环境特异、无普适性，已记入项目 memory |

## 四、建议的落地顺序

1. **先做 `sql-migration-audit`**：纯工具、可立刻用本次的 3 个真实 bug 做回归样例，最快验证"skill 有没有用"。
2. **再做 `atomic-remote-deploy`**：脚本已成品，抽模板成本最低，收益立刻可见（每次发版都用）。
3. **最后做 `linux-server-provisioning`**：体量最大，但它会把 1、2 的脚本当 reference 引用，前后有依赖关系。

4、5、6 建议等前三项跑顺、确认同类项目会复用之后再补，避免一次性造一堆用不上的 skill。

## 五、判断标准（后续新增候选时套用）

一条经验是否值得做成 skill，同时满足这三条才做：

1. 换项目还会遇到（不是本项目特有）
2. 不查资料容易做错，且错了不易自查
3. 能给出确定性步骤或脚本，而不是"注意一下"

只满足 1+2 的，写成 reference 挂到已有 skill 下；只满足 3 的，直接做工具，不必包 skill。
