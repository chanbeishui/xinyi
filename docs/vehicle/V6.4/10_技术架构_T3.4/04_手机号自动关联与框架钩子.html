V6.4 身份流程与员工自动关联（当前权威规则）

来源与范围

用户确认：首次授权默认车主；代驾须申请审核；微信授权手机号匹配现有员工即自动关联；员工—站点由后台直接维护。本章替换旧员工申请、签发绑定凭证、本人消费凭证流程。身份冲突处理、回执去重和锁顺序是本版为落实安全边界选择的技术方案，不是增加每次员工登录的人工审批。

1. 角色和页面

  • 创建新 (app_id,open_id) 账号时只有 OWNER。每次新建登录会话默认进入车主首页；已有有效会话回前台可以保留仍有效视角。
  • availableRoles 由服务端计算：OWNER 基础；DRIVER 必须存在批准过且未撤销的资格；STATION 必须有有效员工关联、有效 sys_user、至少一个有效授权站点及检测工作功能。
  • 员工没有代驾资格时是 OWNER+STATION，不因检测资格获得 DRIVER。停单/证件到期属于实时接单门禁，保留历史和在手任务处理入口，不因角色入口隐藏丢失车辆责任。
  • OWNER 可以进入代驾申请、补正及培训页面；申请接口不要求事先拥有 DRIVER。审核中/驳回不增加 DRIVER。
  • 新登录、切角色、切站、退出、解绑、撤权均不能自动结束代驾承接或释放占用。
  • 不弹注册角色选择；不要求填员工账号密码、员工号、邀请码、OpenID，不提供申请站点表单。
  • 员工关联成功但无可操作站点，显示“已识别员工，暂未配置检测工作权限，请联系管理员”。首次落地仍是车主。
  • 手机号、登录凭据和用户同意分别处理；不在登录时强制索要定位、相机、相册或订阅消息。

2. 统一登录和手机号证明

  1. POST /api/common/login/wechat 仅接收微信登录临时 code。服务端核验 AppID/OpenID，创建或恢复账号，签发 MINI 会话；不接受角色、OpenID、sysUserId 作为身份依据。
  2. 用户主动手机号授权后提交 phoneCode + expectedAccountVersion + verificationRequestId 至 /api/common/phone/bind。phoneCode 与登录 code 不是一个凭据，服务端分别核验。
  3. verificationRequestId 绑定账号与请求；使用 vi_phone_verification_receipt 记录最小回执。只保存凭据摘要，不保存明文 code、session_key、Token。提供本人查询接口。
  4. 领取回执后在数据库事务外调用微信；外部成功后持久化已核验手机号事实。重复处理中返回 PROCESSING，不再次消费 code；结果未知返回 UNKNOWN 并要求查询或重新主动授权，不能凭超时推测成功。
  5. 普通预约联系人电话、个人填写字符串、短信兜底都不能作为新员工自动关联的依据。SMS 可保留已有普通登录功能；如果更换已核验号码，旧员工工作能力需暂停，不能用新号码自动改绑员工。
  6. 员工目录暂不可读时，手机号核验成功与员工工作关联失败分别返回；不回滚已成功的车主登录为“账号不存在”。已授予的员工权限必须读取权威状态，读取失败拒绝工作请求，不用旧缓存放行。
  7. GET /api/common/session/受控会话同步返回最新角色、phoneBound、accountVersion、driverQualification、EmployeeLinkPublic。身份响应 no-store，不经过通用业务响应缓存。

3. 手机号自动关联

使用服务端取得并规范化的国家码/号码，查询框架有效员工；按 DISTINCT sys_user.user_id 计数，不因多部门 join 重复算多名。必须同时满足：

  • 恰好一名有效、未删除员工，且手机号来自受控框架人员目录；
  • 当前小程序账号没有其他有效员工关联；
  • 同应用下该员工没有关联其他微信账号；
  • 账号和员工没有管理员设置的禁止自动重绑状态。 正常唯一匹配直接创建关联，不增加审批。手机号校验成功但无员工/重号/冲突，保持车主能力。小程序只收到粗粒度 NEEDS_ADMIN，不收到其他员工列表、完整手机号或后台权限。

关联表示 AppID/OpenID → vi_account → vi_employee_binding → sys_user；站点在 vi_station_grant/grant_set。产品上表现为用户管理中已绑定微信，不在 sys_user 中复制可独立修改的 OpenID，不给普通客户建立 sys_user，不签发 ADMIN Token。

已有同一有效关联幂等返回。未绑定用户后续才被建成员工，可在新的微信手机号授权后关联；也可通过 reconcile 使用本会话最近10分钟内已确认的WECHAT回执安全重试（技术时效默认值）。持久关联恢复不等于每次请求都向微信取手机号。

4. 并发与框架接入

首次自动关联和员工目录写入使用统一低频目录保护行 vi_employee_directory_guard 的 GLOBAL_DIRECTORY。先保证唯一保护行存在，再 SELECT FOR UPDATE。 锁顺序：目录保护行 → 相关 sys_user 按ID升序 → vi_account/安全状态 → 绑定行 → grant_set/子授权 → 审计/outbox。每次按最新手机号、状态、auth_version、唯一关系重查。微信外部请求绝不放在锁内。 框架新增、导入、改手机号、启停、删除以及个人资料改手机号都须走受控服务/钩子并遵循该保护，不允许普通自助改号未经适用校验成为员工关联权威。若有未纳管外部目录写入，先关闭相关自动工作授权并记录接入阻塞；不能宣称已解决并发。 绑定提交：写关联、相关MINI permission_version/context变化、审计和业务outbox同事务。实际后台人员授权变更继续使用框架统一授权服务与auth_version，不直接写旧关系表。 数据库唯一键是第二道防线。同账号、同应用员工均最多一条未撤销关联；SUSPENDED保留唯一占用，不能因暂停被另一微信抢占。失败审计不得随着成功事务回滚而消失，拒绝日志走独立受控审计路径，不记录明文号码或凭据。

5. 后台站点预配置

GET/PUT /api/admin/station-grants/{employeeUserId} 以原有 sys_user 为对象，完全不要求 vi_account/OpenID/employee binding。 新员工首次返回空集合与 version=0；保存原子创建/更新 vi_station_grant_set，与所有子授权增减、框架auth_version、已关联MINI权限版本、审计和outbox同事务。空集合也保留版本，不能删空后重新从0开始造成ABA。 允许零站点，撤权后回车主/无权限页；不自动回到已无权限的行政所属站点。站点范围与功能权限、部门/公司边界取交集，不把某站配置当作退款、人员管理等全权。 框架角色/站点新增后，员工在前台安全刷新会话即可获得工作入口，无申请和重绑。每个写操作仍实时校验，不能只依赖刷新后的按钮。

6. 解绑、换号与离职

  • SUSPEND：暂停关联工作权限，保留唯一关系及历史；个人车主/独立司机任务不删除。
  • REVOKE：撤销关联并记录原因、操作者、时间；账号 employee_auto_link_blocked 与关联 auto_rebind_blocked 防止下次自动绑回。
  • ALLOW_REMATCH：仅允许本人重新核验；不直接把SUSPENDED/REVOKED改为ACTIVE，不直接绑定前端指定员工或OpenID，不发凭证。需新的微信手机号授权并重新通过全部唯一性检查。
  • 再匹配原同一员工时可以按记录规则安全恢复/新建；跨员工或跨账号身份转移不在普通操作内，保持拒绝并交后台核实，不能静默转移。
  • 框架手机号/小程序核验手机号变化、员工停用/删除：旧工作能力失效/暂停。保留后台人员数据与客户个人历史。必须更新权限版本或权威校验状态；缓存删除失败不延长工作权限。
  • 手机号重复、回收风险依赖人员目录准确维护；本设计不宣称“手机号等于永久劳动关系”。正式上线前核实受控人员手机号维护流程，正常匹配不新增人工审批。

7. 页面和接口退役

O29统一登录；D01是申请入口而不是第二次注册；U01仅切有效身份；U02员工状态/异常；S01工作授权引导。 B26后台直接分配站点；B36查看微信关联、暂停、解除、允许重新核验。 旧 employee-binding/request/credential 写接口从当前主OpenAPI和任务中移除，新的初始化不建 request/credential表。 对已有实现，按实际库及调用依赖做前向停用，旧入口显式拒绝，不留暗中授权通道，不DROP历史记录。没有旧实现则不实现兼容服务。

8. 验收层次

本版新增TC-R62-001～036为真实系统待执行规格；本包的引用策略单元测试、Schema和浏览器演示只能证明各自范围。 必须在真实xinyi+MySQL验证唯一关联/目录变更竞态、重放code、站点预授权、授权撤销、staff不免司机审核、已禁解绑不复活、Owner不误注销。 微信真机与真实手机号接口另在L门禁验证。不得以测试场景开关模拟生产微信认证。

手机号完成后的会话接续

手机号回执不携带Token。requiresSessionRefresh=true时，客户端先通过现有refreshToken调用/api/common/token/refresh，原子保存新访问/刷新令牌及新角色，再查询关联或切工作视角。权限变化不阻止基础账号合法REFRESH；旧工作角色失权时安全回OWNER。响应丢失先查本人的receipt，必要时先刷新，不重复消费一次性phoneCode。所有重试均防并行刷新和旧响应覆盖新会话。
