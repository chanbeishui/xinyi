2.4 手机号一致时自动关联现有员工

系统使用微信授权且由后端核验的手机号，匹配原框架“系统管理 → 用户管理”的有效员工手机号。正常情况下唯一匹配、双方无冲突，就直接建立微信账号与该员工的关联，不等待管理员签发凭证，不要求员工再次确认绑定。

产品效果：后台用户管理能够查询“该员工已关联微信”；小程序随后读取该员工实际获授的站点和功能权限。实现关系为：

微信 AppID＋OpenID → 小程序账号 → 员工关联 → 现有 sys_user → 后台授予的站点范围

不必在多处复制可独立修改的 OpenID；普通车主不创建为 sys_user。预约联系人电话、个人自由填写号码、客户端提交的员工 ID 都不是员工识别依据。小程序不会因匹配到管理员而获得后台 Token 或全站权限。

后台先给员工配置 A、B 站 → 员工微信授权同一手机号 → 自动关联 → 默认进入车主首页 → “我的 → 切换身份”选择检测工作人员 → 查看并切换获授权站点。

2.7 暂停、解绑、换号及撤权的例外处理

B36 只用于查看关联和处理异常。正常登录不经过它的审批。

  • 暂停：停止员工工作能力，保留关联与历史。重新登录不能直接解除暂停。
  • 解除：撤销工作关联并阻止同号登录自动绑回；保留车主档案和独立代驾记录。
  • 允许重新核验：只开放再次核验机会，本人完成新的微信手机号核验且满足唯一匹配后，才恢复工作能力。点击这个按钮本身不恢复权限。
  • 手机号变更、员工停用／删除、站点撤权：及时让旧工作权限失效，不依赖前端是否刷新，不影响已经成立的车辆返还责任。
  • 不覆盖另一个微信账号或另一名员工的有效关联；重号、旧号回收、人员目录维护错误由后台核实。技术保护不等同永久证明劳动关系。

2.8 接口、数据与角色切换边界

手机号核验回执与员工关联结果分别记录；无法确认外部核验结果时不能重复消费旧凭据或假定成功。具体字段、并发锁、账号唯一性、目录钩子、令牌更新和审计规则见 10_技术架构_T3.4/04_手机号自动关联与框架钩子.md 与主 OpenAPI。

角色切换、登录退出、撤销员工关联都不自动结束代驾承接，也不改变车辆保管方。退出仅撤销当前会话；再次登录重新核对既有资格，不丢失资格和历史。

当前开发基线不再提供员工申请、管理员签发绑定凭证、本人消费绑定凭证的正向流程。已有实现只作受控前向停用并保留历史，不能物理删除用户数据。

3 端到端流程、预约与派单规则

3.1 正常履约

车主选上门时段 → 填接车地址 → 补齐或复用车牌车型 → 服务校验、站点匹配和报价 → 确认并建单预占 → 选择已启用方式，微信可信支付或线下全额核实 → 到计划时间派单 → 代驾接受 → 出发 → 到达 → 车主交车 → 到站 → 站点收车并进入检测中 → 登记真实检测结果 → 站点放行 → 代驾取车返程 → 实际归还交接 → 立即释放司机 → 车主服务确认或24小时自动完成。

3.2 上门时段与站点容量

对外的预约时间只表示约定上门接车区间，不表示车辆同一时间已经到站。客户先选候选时段，不预占某个未匹配站点的额度；地址、车型齐全后校验可服务性。用户填写失败或返回修改保留已填信息，不默认换时段。已有车辆可预填，不强迫先补全部证件。

P04建议区分两类额度：服务区域上门时段的接送额度；检测点内部接收排期额度。内部排期用上门区间、交接耗时、地图行车时间和缓冲估计；接收能力不符时拒绝最终报价/建单，不能先收钱再发现容量不足。首期可按保守人工配置额度实现，不要求先做复杂排程优化算法。

同一事务创建订单、保存报价快照并预占名额；支付成功把同一预占转为正式占用，不再扣第二次。30分钟到期按所选渠道确认未付或进入资金核实，未使用名额不无限续占；线下证据待核实的到期分支见第23.4节。可信关单后只释放本订单尚未消耗的名额。站点已实际接收/检测消耗的容量不得因事后退款重卖。

3.3 计划派单

计划时间dispatchAt=pickupSlotStart−dispatchLeadMinutes。N由后台配置并保存版本。付款时未到计划时间为SCHEDULED；到时且仍有效才开始派单。付款完成已经超过计划派单时间时，在满足最短预约提前量与运营可服务条件下立即安排，不允许为过期时段无限补派。

参数变更默认只作用于新订单。需要作用于未派单既有预约时，提供“受影响订单预览→明确确认→更新计划版本”的独立操作；不能重派已承接订单。

3.4 司机候选与公平轮转

正式资格有效、账号允许新接单、证件有效、开启听单、位置足够新、在派单半径内、无有效邀约和在手承接，才进入候选。单靠“没有未完成订单”不正确：车辆已还、订单待确认时司机已空闲。

V2同时写全局轮转和距离评分优先，本版按P01提出单一策略：全局游标决定自动顺序，距离只过滤可服务半径；人工候选列表可排序。单人邀约默认60秒、原建议半径5公里扩8公里、自动总截止5分钟，均需运营确认配置，不变成无法改变的代码常量。总截止优先于跑完所有候选；多实例派单对游标和占用原子处理。运营发人工邀约仍须司机接受，不能后台单方面把未响应司机认定接单。

3.5 代驾取消承接

未接车取消承接必须二次确认，和接车动作互斥。成功后只结束本承接，保留原车主订单、原支付、原站点预约与历史记录，按原流程重新派给其他代驾。停单一轮、当日3次停止新接单、北京时间自然日清零是V2既有建议规则，轮次定义和申诉恢复口径列P01，不采用事故7/30天处罚。

3.6 司机释放

正常归还交接成功即释放；批准取消的返还交接成功、正式取消与释放同一事务完成；未接车司机取消承接或订单正式取消也释放对应任务。站点收车、检测完成、上传照片、通知车主、切角色均不释放。释放删除的是占用关系而不是历史司机记录；详见F31。

4.4 关键并发

取消审批与接车相遇：锁同一订单并重读当前保管方，先成功的事务决定后者分支。归还与争议相遇：归还记录与释放不可被争议回滚，争议仅影响服务确认。PC与小程序同时提交结果：相同幂等键同请求重放原结果，不同内容冲突，绝不静默覆盖。晚到自动完成不能释放该司机的新任务。

所有动作、前置条件和同事务副作用见05_数据设计/业务动作与状态事务矩阵，具体动作以本包当前事务矩阵为准。写接口使用具体业务动作，不提供targetStatus通用改状态接口。

5 计价、支付、取消、退款与对账

5.1 配置计价

车型采用框架数据字典的稳定编码，标签可修改、项目可启停，历史订单保存编码及当时标签。字典新增不自动代表检测点支持该车辆，也不自动产生价格或驾驶资格兼容关系。新车型未配服务能力/价格时不可下单。

计价规则至少包含：适用车型、检测类型/套餐、适用服务范围、检测费用、代驾起步价、含里程、超里程计费单位与单价、路线口径（单程或往返）、进位方法、生效时间、版本、审核状态。规则冲突必须显式处理，禁止随机命中第一条。

金额以分计算。示意计算为：检测费 + 起步价 + max(0,按配置口径路线距离−含里程)按配置进位后的单位数×单价；这是可配置公式示意，不指定任何实际价格。取车里程与归还里程用于留证，不作为首期计价距离。等待费不能在尚未发生等待时精确预收，启用方式见P02；未确认不自动补扣。

5.2 报价与建单

报价绑定账户、车型、地址、时段、匹配站点、路线摘要、规则版本和有效期；报价不占名额。确认建单时原子校验报价未过期且名额有效。新订单固定应付金额和规则快照，配置改价不追改已建单。客户端只提交quoteId和已确认输入，不接受金额、操作者ID或任意站点归属。

5.3 支付方式、可信收款与关单

支付设置的线下/微信开关相互独立。O10从服务端按订单主体读取有效方式；双关暂停新付费预约，不把价格变成0。微信开启须具备完整且已发布商户，不能仅填写商户号就标记可用。完整字段、四组合矩阵和版本发布见第23章。

首次微信预支付或线下意向成功创建时锁定支付方式与收款身份，不混合支付、不悄悄切通道。微信预支付time_expire与原订单30分钟截止一致；客户端重试不续期，requestPayment结果不直接置SUCCESS。回调验签解密并核验AppID/商户/订单/金额，通知缺失主动查单。

线下选择不是付款成功。后台登记真实全额收款凭证并独立核实后，才写支付成功和派单事件。无证据到期按未付关闭；已有凭证或渠道未知结果，不武断宣布未扣款，进入资金核实，原名额不无限占用；迟到确认须校验原预约时间和重新取得容量，否则人工处理资金与履约冲突，不自动复活旧预约。详见23.4。

当前开关只控制新的付款入口，不停历史回调、查单、退款和对账。关闭微信后已发预支付会话仍可能付款；系统必须按可信事实收敛。新订单更换商户不改变旧订单商户身份；在同一商户内受控密钥轮换不导致旧退款永远使用失效密钥。

5.4 取消与退款合并为一份售后申请

取消回答“这次服务是否继续、车辆如何归还”，退款回答“已收款退多少、是否已到账”。这两件事实不同，但不应强迫车主提交两次、运营审核两次。本版合并申请入口、审核列表、详情和决定；订单履约、实际保管、渠道资金继续分开记录。

申请类型仅两种：CANCEL_REFUND（取消预约，并一并决定退款；批准金额可以为0）与REFUND_ONLY（仅退款，不取消服务；批准金额须大于0）。车主只能对本人订单提交；后台代办明确实际操作主体与授权。尚未支付的30分钟关闭不是退款申请；主动未付关闭仍是P06建议。

一个订单同一时间只有一个未办结售后申请。重复提交返回原申请入口，不重复预留资金。申请说明和追加证据保留历史，不可在审批后直接改批准金额。金额变化需显式撤回/修订并重新审核受影响部分，不能改已成功的退款事实。

审核界面同时展示订单/车牌、客户、申请类型、当前是否接车、当前保管方、承接ID、实付/已退/预留/可退、拟批准退款、审核意见、结果预览。提交必须同时具有统一审核与相应资金权限；原先只有“取消权限”的账号不自动获得退款能力。可以把权限授予能一次完成审核的人员，不通过制造第二个人工审核任务解决。

5.6 退款执行、幂等与对账

批准金额不得超过实付－已成功退款－其他有效退款预留。预留涵盖等待返还阶段，防止另一个申请先用掉这笔额度。原退款号由caseId和审核版本关联唯一生成；金额为0不发渠道请求。网络未知结果继续保留金额预留、查询原退款号；微信仅可信渠道成功才计入已退；线下仅已批准金额的实际退款凭证经独立核实后计入已退。

主售后只有一份审核决定，退款执行单仍独立存在，用于渠道调用、回调、查询、异常追踪；这不是第二份退款审核。后台原B13/B14与B29合为“取消与退款”。客户支付渠道对账仍为B31，不与代驾报酬对账混淆。

取消服务性退款的执行时点采用“有车先还车”的本版默认，属于实施设计Q01，模块评审可调整；无论何种退款时点，都不能以退款成功代替实物归还。外部支付错误的人工退款另按真实渠道证据处理。

7 车况证据、交接码与文件管理

7.1 发生哪些节点，就保留哪些节点

正常服务有四个拍照节点，每节点前、后、左、右、仪表盘、内饰六类，另可追加损伤说明。取消发生在未到站时，只要求已经发生的接车与归还节点，不强迫伪造到站和站点取车。已经到站/出站的取消单仍保存相应真实证据。

接车与归还里程必录，范围和位数由统一规则校验，建议DECIMAL(10,1)、对外十进制字符串。中间节点可选，已填不得倒退；归还小于接车需复核，仪表更换等异常不能仅靠客户端reason跳过。大幅异常依据配置的路线预期与阈值提示，不自动定责或计费。保留原始值、更正值、理由与操作者。

上传凭证绑定账户/业务类型/订单/节点/文件限制，服务端验实际对象、内容类型、大小、归属与哈希后才READY；客户端提交ossKey或hash不能自证完成。文件使用私有存储、短期授权查看，敏感原图另校验。

节点提交时封存照片版本；重拍在封存前更换草稿版本，封存后只能追加更正说明，不覆盖旧图。水印由服务端生成，记录采集时间、接收时间与位置来源；水印不能把伪造GPS变成真实定位。照片只是证据之一，不自动判断法律责任；不得因车主已服务确认而机械拒绝后续合理争议。

8 通知矩阵与时效

10.2 四视角投影

10.3 数据类型与并发

11 安全、隐私与审计

遵循原PRD最小可见和真实归属校验：车主看本人，司机仅履约必要期间看已分配订单的必要信息，员工在授权站点按功能操作，后台全局能力需显式授权。历史任务保持审计关联但降低地址、电话和证件可见性。

敏感文件均私有访问，证件原图、批量导出需目的、理由、有效期和独立审计。秘密、令牌、支付证书、明文身份证、交接码不进入日志、埋点、源代码或前端包。文件URL不是权限，签名过期刷新时必须重新鉴权；导出下载同样复核权限。

站点权限变更、身份绑定、代驾审核、人工派单、取消批准、退款、结果更正、敏感查看与越权拒绝记录操作者、时间、前后状态、原因和来源；领域流水和框架安全日志均需保留，不以一条“操作成功”代替全部事实。

原文“首期不自动删除照片”尚不足以上线。证件、车况、支付对账、审计、争议资料的保存期限需分别批准，并有到期处理、删除请求与必要争议留存的人工流程。个人信息保护法的目的必要性、最短必要保存、敏感资料保护是外部核验，不自动得出统一3年/180天适用于全部资料的结论；详见外部依据文件。合规负责人应结合实际采集与供应商确定落实方案。

18 第一性原则复核与可用性检查

18.1 这个项目到底要保证什么

核心不是做115张页面，而是完成四件事：在承诺时段找到能服务的人；始终知道车由谁保管；让真实检测结果对应正确车辆；使每笔钱及其退款可核对。身份、时段、司机占用、车辆交接、资金分别是事实，不能用一个订单状态替代全部事实。

18.2 原理层面可实现，服务承诺需要验证

本次范围未显示必须依赖不可实现的技术。统一账号多角色、定时派单、受控交接、结构化结果和支付退款可以分模块实现。这个判断是设计可行性分析，不是代码或供应商已验证，也不提供没有数据支撑的落地成功百分比。

剩余最大风险是现实资源与软件承诺不一致。以“每名司机每天可工作8小时、每单平均占用2小时”为演示假设，50名司机理论上限50×8÷2=200单/日，尚未扣休息和波动。要达到500单/日，平均占用必须≤48分钟且利用率达到100%。这些数值是算例，不是项目实测；应记录接车准备、司机到上门地址、往返行车、四次拍照交接、检测等待，以及司机结束后到下一单的交通成本，再配置可约名额。

18.3 一车一保管事实

照片上传、发送消息、审核取消、退钱都不能代替把车实际还给车主。若车在站点而司机显示空闲，或订单取消了却没有返还责任人，系统就是逻辑不完整。C09–C11解决了正常释放与取消承接的区别，还需用I02–I05保证并发条件下也成立。

司机接车和归还后的自身交通方式、夜间无人接收、车主迟到、无法安全行驶的检测不合格车辆等，软件不能自行消除。首期不做事故和保险模块依照用户决定，但现实异常仍需线下运营处理、明确联系人和车辆保管，不得擅自宣称无风险或已投保。

18.4 配置化不能掩盖计算语义

车型可新增、价格可配置是正确方向，但车型标签不是合法准驾判断，报价表也不能决定未来未知等待时长。应明确单程/往返、进位与生效版本；等待费启用前补用户确认与收款方式；新增车型关联服务能力与司机资格兼容，不仅多加一条字典。

18.5 自动派单不等于一定有人接

支付发生在未来，不代表未来有司机。只锁站点工位不锁上门供给，可能卖出永远不能准时接车的订单。先时段再地址可以作为交互，但地址未知时不能承诺某站名额。调度提前N分钟配置也不代表N必定足够覆盖司机到车主的路程；需要实际时长、缓冲和人工兜底。

18.6 角色包含不等于一人可以给自己证明

检测员工有车主和经审核的代驾资格，没有技术矛盾；但同一个人切两次角色不能构成独立站点交接双方。P03需要结合班次人员确认；不能为了页面顺畅把交接码直接返回给核验方。

18.7 结果、证据与通知各有边界

“检测中”只记录站点已经接收本次业务，不要求自动读取检测仪器；“合格/不合格”是人员登记结果，不是系统实际完成物理检验。照片可辅助追溯但不能保证覆盖所有损伤；通知发送成功不能证明对方看到。既不扩做复杂功能，也不能夸大已做功能的证明能力。

18.8 尼尔森可用性落实

持续显示当前角色、站点、车辆保管、取消待返还与资金状态；把“车辆交接完成”和“服务确认”用不同文案；保留返回、草稿和客服出口；用禁用原因代替不明消失按钮；不同角色复用一致字段与验证码规则；报价变化要二次确认；取消退款入口可见但不抢主操作；失败重试不重复收费；所有无权限/弱网/文件未完成均有可恢复提示。

结论：可开展已明确范围的分阶段开发。仍需在指定模块评审P01–P08、上线前落实L01–L06，而不是继续把所有旧图和旧建议一起扔给Agent，让代码替产品做决定。

19 自由勾选组单、个人对账与行内核价（V6.4 已确认）

19.1 术语与边界

核价是确定一次真实服务应给代驾的报酬；对账是按一个费用承担主体、一个代驾、一个币种，按明确勾选的服务核对明细和合计；付款核对是核实系统外已经发生的付款。三者不能合并成一个状态，但核价不再是独立页面或对账前必须跳出的流程。

本轮用户已确认：在个人对账每条服务明细提供「填写价格／修改价格」，草稿允许待核价；人工改价集中整单独立复核；司机确认后或有付款记录原账只读，从原行申请后续调差。客户实际收费、退款金额、司机占用和全局费用规则不被本操作修改。

本期仍不做钱包、提现、自动转账和分账。每一对账单只包含同一个payorEntityId、driverId、CNY下明确勾选的费用条目。日期是可选查询条件，不是组单成员；同日可多单、可跨日/月选择。服务日期跨度由实际成员推导，仅用于说明；查询截止日按Asia/Shanghai转换为次日排他边界。未提供的真实费率、取消补偿及主体配置继续待确认，演示数值不作为上线标准。

19.2 服务结束先留事实，费用未定不锁司机

真实任务结束事件包括正常实际归还、取消批准后的实际归还、接车前合法解除。结束事务先完成车辆保管、承接和司机释放并写outbox；异步按主体、代驾、源事件永久去重形成费用源。客户订单号不是唯一费用来源键，多次重派分别保留承接。

有生效规则时保存规则计算金额与版本；未匹配规则时保存NULL和待核价，不填0。明确约定为0元与不知道多少钱不同。费用计算/事件消费失败可重试，不能阻断已完成的车辆返还。仪表里程保留为证据，不直接当成报酬路线。

19.3 个人对账汇总与明确勾选组单（本轮确认）

入口：B28代驾员列表→某位代驾「对账」，或B37对账列表→「个人对账」，进入B42汇总，不默认打开最近一张账单。B38继续作为一张具体账单的详情/核价工作页。

弹窗标题为「填写/修改本次代驾报酬」。只读显示代驾、任务、车辆、服务类型、规则计算金额、当前拟金额。必填「修改后应付金额（元）」和「修改原因/计价依据」，可关联已有记录或补充凭证，不强迫每次重复上传。

输入的是本次服务最终拟应付总额，不要求同时填写差额。例如60→70→65，最终拟价是65，不能累计+10再+5。金额转整数分后保存；服务行允许明确0元但需原因，不接受负金额。负调整仅通过专门调差记录。生产上下限由授权费用规则确定；演示上限不可作为生产默认。

服务端读取旧金额并计算差异；客户端不传原值作为可信事实。不影响客户收费、退款、司机资源、计费规则版本或以后订单。保存工作行、修改历史、账单内容版本和操作审计同事务完成。取消弹窗不写入；未保存关闭要提示；保存失败保留输入。相同金额不产生重复改价事件。

19.5 整单内部复核与发送

没有人工填价/改价且全部按已批准规则计算：获授权人员核对后「发给代驾核对」，不增加逐行核价步骤。

有任何人工填价或改价：经办在同页完成多行修改→「提交整单复核」→另一名获授权人员在同一张账单检查变更摘要、逐行依据和总金额→「复核通过并发送」，或「退回修改」。不再要求到B41为每笔拟价分别申请审批。

复核记录绑定整张账单的内容revision和规范化hash。复核者不能是本次提交人、当前提交版本的任一人工改价参与人或该司机实际本人；通过账号受控绑定比较真实主体，不比较两个域的数值ID。曾参与改价后又改回原金额，仍保留历史，不清除贡献者记录以绕过复核。

待填写金额为0笔才能提交复核/发送；人工改价未经当前版本复核不得通过直接send接口绕过。批准需要同时具备复核和发送权限；批准决定、状态SENT、已发布快照、outbox在一个事务完成。通知失败不退回复核，不重复发送账单版本。退回状态回DRAFT并保留原因和待审快照。

19.7 草稿拟价与最终台账结转

实现设计：源服务费用台账不可覆盖，草稿只改工作副本，复核和反复发送只产生审批及快照。司机确认成功的同一事务，按每个本轮人工核价行追加一次最终核价记录/差额台账，并直接绑定该账单；不得作为未来可选费用再出现。

源金额已知时，结转差额=确认金额−原已计入组成金额；相同金额只留审核不重复入账。源金额NULL时，追加INITIAL_VALUATION表示第一次核价，不能把源NULL篡改成历史0元。生成键包含主体、源条目、账单和确认修订；数据库唯一约束保证重试只产生一份。账单行显示最终金额一次，不能把源金额和最终金额再次相加。

具体逻辑表、唯一分配和锁顺序见05_数据设计及10_技术架构_T3.4。此处的持久化分层是落实简化流程的技术设计，不是财务法规结论；旧客户交易无迁移要求；E03负责新vi首次建表，既有sys接入需隔离验证。

19.8 已确认或有付款记录后的调差

19.9 代驾确认后的付款凭证闭环（本轮确认）

顺序：整理所选服务→完整价格及必要内部复核→发给代驾→本人确认指定版本→实际付款发生在系统外→B38录入付款凭证→独立核实→更新付款状态。对账确认不是收款确认；上传一张文件也不能直接置已付。

凭证表单只读带入账单号、代驾和费用主体；填写实际付款金额、时间、主体内唯一外部流水及凭证文件。文件必须经服务端核验READY并具备查看权限，前端文件名或URL不能自证可信。登记与核实分开；另一位获授权人员核验收款对象、金额、日期与流水。未接入真实付款数据时不得伪称已查实。

付款状态与对账状态分开：NOT_READY（未确认）；UNPAID（确认待付款）；PARTIAL（部分付款）；PAID（已付清）；NO_PAYMENT_REQUIRED（确认0元无需付款）；OFFSET_REVIEW（负净额待人工）。凭证另有PENDING/VERIFIED/REJECTED/REVERSED。只有净核实付款影响已付；待核实凭证只保留可登记预算。

剩余待付 = 已确认净应付 − 净已核实付款。可登记金额 = 剩余待付 − 待核实凭证金额。登记和核实都锁父账单并重查余额；同主体流水不重复登记。待核实凭证不等同已付款，退回/冲正不删除历史。UI给出具体凭证待处理，不因预算预留让操作无提示地锁死。

首期按整张账单支持部分付款，不额外建设逐服务分摊。300元账单核实200元，账单剩余100元；所有关联服务提示“所在账单部分付款”，不能自行认定某两条已结清。整单付清后相关服务退出默认未结清列表，历史仍在。0元账单确认后无需付款，不强制上传不存在的凭证；负额按已有人工处理边界，不自动扣款。

本轮正常付款记录一条关联一张已确认账单；一笔实际银行流水若涉及多张账单，不允许复制同流水伪造多笔，应进入人工差错核实并评审付款分配扩展，不隐式上线跨账单拆分功能。存在任何付款记录，原账内容均锁定，不通过删除凭证解锁。

本系统不发送转账、提现或分账指令。实际费用主体、真实报酬标准、取消补偿、付款岗位及凭证采集细则仍需业务配置；本次确认的是流程和界面，不是实际付款授权。

客户线下退款：继续一次售后审核，金额预留并等待必要返还；实际退款在线下进行，后台登记退款流水/凭证并独立核实后计入已退。不得调用微信退款接口、不得默认“原路退回微信”，也不能把一张截图当成供应商已确认。原来微信收款的订单仍必须按原商户退款，不能因当前开关关闭或商户更换改为线下。

23.7 保存、校验、发布与停用

所有配置采用同一规则：编辑 → 保存草稿 → 校验 → 查看影响 → 保存并生效。保存草稿只形成新草稿版本，不覆盖当前正在使用的有效版本；校验结果绑定草稿版本和内容摘要。修改一项后原校验失效，不可用旧PASS发布新密钥。

发布请求带expectedVersion、draftRevisionId、validationId、内容hash、变更原因；同一事务检查权限/归属/依赖/最新版本，记录不可变发布历史并原子切换activeRevision。两个管理员并发提交后者409，保留未保存内容并提示重新核对，不静默覆盖。停用/双关提示待支付、在途消息和历史退款影响；敏感配置发布须最近后台再认证，但不额外制造多级业务审批流程。

本地格式校验永远不发短信、不创建扣款。只读连接检测独立按钮，精确显示检查了什么；真实短信/订阅测试须二次确认、白名单、限额、测试权限，可能产生费用或消耗订阅次数。真实支付退款联调是独立授权测试，不绑到“保存”按钮。演示原型的“使用测试样本”只改变本地演示状态，不能成为真实联调证据。

发布后无需改源码或重启。关键支付写入前读取权威activeRevision，按不可变版本缓存配置；outbox通知实例刷新缓存，但发布正确性不能依赖Redis广播成功。实例未能读取权威版本时拒绝新交易或等待，不以旧“开启”值放行。前端成功提示包含生效版本和时间，重新进入读取有效值。

新交易固定商户身份、AppID、收款主体和非敏感配置版本。历史操作仍使用原交易身份；同商户密钥更新通过受控凭据环服务新旧交易，不永久绑定过期签名私钥。停用不删除历史验签和退款材料；更换商户不能把旧退款发给新商户。消息在生成delivery时固定模板及通道版本，发送前仍检查停用、事件时效和授权；停用阻止尚未发出的消息，不删除已接受记录、不停止回执核实。

回滚也是一次新发布：目标版本必须重新通过当前依赖/密钥有效性校验，不能恢复已泄露密钥或无效模板。已有金融和发送记录只读不追改。

23.8 安全、提示和验收

密钥/私钥/AppSecret只允许专用写入，不出现在GET、导出、前端localStorage、错误、日志、审计diff、截图样本或普通sys_config。已配置显示“已配置（某时间/版本）”，不回显原文；空输入表示保持原值，替换/清除必须明确选择，不能把“******”存成新密钥。根主密钥与密文数据库分离。

管理员只能操作授权组织/收款主体；读取、编辑、发布、测试、凭证登记和独立核实分别授予权限。可配置商户不自动允许退款审批；可查看站点不自动允许看整个企业云密钥。第三方网关域名固定白名单，回调基址来自部署信任配置，禁止任意URL探测。

发布不完成的字段必须精确提示：例如“开启微信支付前请填写商户号”“APIv3密钥须为32字节”“腾讯云模板第2个参数未映射”“订阅模板字段time2缺少来源”“当前草稿已修改，请重新校验”。无订阅/通道停用/参数错误/供应商超时使用不同错误码和恢复入口。

重点验收：四种支付开关组合；微信缺商户拒绝生效；草稿不影响付款；关微信后旧退款回调正常；同商户密钥轮换；线下登记不派单、独立核实全额才派单；过期证据不复活名额；腾讯与阿里参数正确；同事件不广播双发；未知结果不跨云重发；无订阅不阻断业务；模板变更不沿用旧授权；多实例配置一致；敏感信息永不回显。

完整字段字典、动作契约、数据约束和测试案例为本章的规范性组成部分，位置分别为04_接口、05_数据设计、06_验收和10_技术架构_T3.4/05_第三方配置与运行时。
