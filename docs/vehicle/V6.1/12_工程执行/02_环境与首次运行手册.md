# 环境与首次运行手册

## 1. 前置软件和作用

运行工具：Python3.10+；开发基线JDK21（编译release17）、Maven3.9系列、Node22、Docker Engine+Compose v2。版本由doctor实际记录。没有mvn时可通过MVN环境变量指向IDE内的完整mvn/mvn.cmd路径，不假设系统PATH已有。执行的argv不经过shell拼接。

本包只锁定新增工程的直接依赖意图，不伪造实际解析lockfile。小程序模板使用本轮官方uni-preset-vue vite-ts记录的DCloud版本系列；E04第一次在有包仓库访问的工作区执行npm install，提交产生的package-lock；随后用npm ci。镜像先pull并通过lock_images.py将实际RepoDigest写images.lock.json；断网失败保留状态，不猜digest。既有PC lockfile照用，不为统一强制重解所有依赖。

## 2. 初装顺序

```bash
python docs/vehicle/V6.1/12_工程执行/engineer.py env --repo . --apply
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind infra
python docs/vehicle/V6.1/12_工程执行/lock_images.py --repo .
python docs/vehicle/V6.1/12_工程执行/database.py inventory --repo .
python docs/vehicle/V6.1/12_工程执行/database.py bootstrap --repo . --confirm-db xinyi_vi_dev
python docs/vehicle/V6.1/12_工程执行/scaffold.py --repo . --apply
```

env只生成随机本地密钥、固定隔离端口与gitignore，不打印密钥。infra使用MySQL33306、Redis36379、测试供应商19091，都只发布127.0.0.1；应用18080。与既有3306/3307/6379分离，不接管现有服务。端口冲突可以在`.env.vi.local`调整，记录改动。

bootstrap只允许全新本地白名单库名，提取实际框架SQL中的sys表CREATE/初始INSERT，排除DROP、USE和旧vi语句，再执行66张当前vi建表。导入后重置新隔离库的admin为随机密码、停用其他框架示例用户。凭据不输出、不提交。中途失败不能静默继续，需要保留现场在新隔离实例排查。业务fixture在E07通过受控服务创建，不包含真实客户。

**本脚本不向已有xinyi数据库写入，也不把任意指定远端库当“测试”。**用户未做M0，按03的框架初装路径执行；原库保留，本包使用新隔离库。意外同名表先核查，不预设存在旧M0，也不执行自动迁移。

## 3. 工程构建

scaffold以dry-run为默认，--apply仅复制不存在的模板文件及必要POM声明，冲突先拒绝并记录，不覆盖已有源码。单独存在xinyi-vehicle时根据E00映射处理，不建重复模块。

```bash
npm --prefix xinyi-miniapp install
npm --prefix xinyi-miniapp run type-check
npm --prefix xinyi-miniapp run build:mp-weixin
npm --prefix xinyi-ui ci
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind backend-build
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind pc-build
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind backend-run
```

实际后端jar名若与xinyi-admin.jar不同，E00在workspace/commands中明确修改后运行；不通过找第一个jar蒙混（可能选到original或tests）。backend-run以druid,vi-local覆盖本地连接，额外配置路径在包中；不能误加载真实生产数据源。

模板只有工程联通页面和API请求基础，后续业务任务必须实现真实页面。小程序AppID由实际微信项目填写；不伪造可用生产AppID。H5启动不是微信上线；真机localhost指手机本身，L02通过受控开发域名/代理联调。

## 4. 真实测试

数据库已初装可运行db-test，它只检查真实MySQL的结构和特定SQL不变量。业务HTTP测试必须先实现E07测试控制面并启动vi-it；不能直接将只支持生产profile的jar通过permitAll变成测试服务。

```bash
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind db-test
# E07和对应身份业务完成后先用integration-identity；身份与报价都完成后才能运行下面全套19项。ViHttpSuiteIT启动嵌入式HTTP服务器
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind integration-suite
# 或已有受控vi-it测试进程使用本地固定端口时：
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind live-test
```

无法访问真实后端时测试必须失败，不能skip。测试运行有隔离库guard和profile确认；HTTP Server实际提交的数据库事务不会因为测试方法加@Transactional自动回滚，必须按runId独立夹具或销毁独立环境收尾。不得删生产资料“清理测试”。

## 5. Docker不可用与Codex云端限制

先记录docker版本/权限实际结果。可在获授权的本机独立安装MySQL/Redis/Python测试服务，继续使用相同端口、guard和测试；或用户配置一个专用短期CI执行器，不允许退化为H2/SQLite来声称MySQL通过。没有任何MySQL执行能力时，可继续纯代码/契约任务，数据库与真实HTTP验收保持ENVIRONMENT阻塞。

网络限制只阻依赖解析/镜像拉取；保留lock意图和失败日志，后续在相同基线下恢复。Codex的沙箱/命令审批由用户配置，包内不提供绕过脚本。生产部署不由此手册自动触发。


## 阶段化测试，避免M1被尚未实现M2卡死

`integration-identity`只收集10项身份/资料真实HTTP测试，使用IDENTITY夹具：基础测试身份、框架授权和车型字典，不依赖报价/支付。`integration-booking`收集9项报价测试，BOOKING夹具扩展站点/时段/价格，依赖C02–C04。`integration-suite`运行这19项；`integration-full`再运行所有任务新增的*IT。没有收集的后续场景仍为NOT_RUN，不记为通过。

E07分步完成FixturePort：先IDENTITY与守卫，后续C02/C03/C04分别补BOOKING所需构造。测试夹具只提供业务前置，不生成已经支付/交接/确认/付款的终态。原资料“BASE”统指基础夹具族，不作为请求字面量。

工作区ci-stage.json从FOUNDATION→IDENTITY→BOOKING→FULL按代码能力逐步前移。所有PR仍构建/执行基座和数据库检查；未进入的后续阶段明确未验收。G01最终门禁要求FULL，不能以FOUNDATION工作流绿色称完整交付。

```bash
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind integration-identity
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind integration-suite
python docs/vehicle/V6.1/12_工程执行/engineer.py run --repo . --kind integration-full
```
