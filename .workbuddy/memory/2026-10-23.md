1. **Mapper 必须放 `com.xinyi.**.mapper` 包**：`@MapperScan("com.xinyi.**.mapper")` 只扫这个包名，

6. **打包只能用独立 Maven** `/e/codex/.cprep/tools/apache-maven-3.9.16/bin/mvn`；
   `logs/mvn.sh` 手拼 classpath 会因缺 `com.google.inject` 崩，`logs/build_backend.sh` 只做 javac 校验不打 jar。
7. **前端构建不能清空 `dist`**：沙箱批量删除保护会拦 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`（>50 文件），

## 第三轮：上游 `ck_ver_*` 约束笔误的直接修法

用户指示：资料包 `CHECK (version >= 0)` 引用不存在的列属于上游 bug，**直接改**，不要只记录在案。

### 结论：不是加列，是改表达式
`vi_driver_statement_membership_change` 是"对账成员变更**不可变历史**"表，只追加、永不 UPDATE，
本来就不做乐观锁，所以没有 `version` 列是对的。上游那套 `ck_ver_<表名>` 是按"所有业务表都有 version"
批量生成的，到这张表落空。给它加一个永远为 0 的 version 列 = 乐观锁语义名存实亡 + 改了资料包结构。

落地（`migration_20261023_04` 第三节，幂等）：
```sql
ALTER TABLE `vi_driver_statement_membership_change`
  ADD CONSTRAINT `ck_ver_driver_statement_membership_change`
  CHECK (`revision_before` >= 0 AND `revision_after` >= 0)
```
- 约束名**沿用上游原名**，避免与资料包逐表比对时出现"少一条约束"的假差异
- 实测：`revision_before=-1` → `ERROR 3819 Check constraint ... is violated`；正常值可写；回滚无残留
- 新增验收 `S6c`：同时断言"约束存在"+"表里确实没有 version 列"，防止以后有人为对齐资料包偷偷加列

  （原包备份 `同目录/*.zip.bak-20261023`，用 Python zipfile 重写单条 entry，1914 条 entry 数量与完整性不变）
- **实测影响面比预想大**：原始包灌空库报 `ERROR 3820 ... non-existing column 'version'`，
  中断在第 1256 行 → 79 张表只建成 **56 张**，后面 23 张全缺；修正后一次建成 79 张。

## 第四轮：连跑全量时暴露的两个时序型缺陷

改完 SQL 后连续跑全量，先后冒出两条不同的偶发失败——都不是抖动，是两个真的时序缺陷。

### 1. STK-010：并发刷新"失败方"的提示取决于对方事务何时提交
`AuthService.refresh()` 原来把 `consumed_at != null` 与 `revoked_at != null` 并成一个条件，
统一报"刷新令牌已失效"。但成功方消费令牌后还会 `revokeTokensBySession`，把刚消费的那张也置 `revoked_at`，
于是失败方先命中哪个条件全看时序：早到 → `consumeToken` 返回 0 →"已被使用"；晚到 → 走到 392 行 →"已失效"。
拆成两步判断，**更具体的原因优先**：先 `consumed_at`（"已被使用，重试没用"），再 `revoked_at`（"已失效"）。
现在无论谁先提交，失败方都拿到"已被使用"，提示不再抖动。

### 2. SR-006：无候选订单被反复扩圈，留痕重复
`DispatchService.dispatchOrder` 的 `startRound` 取 `maxRoundNo`，它算的是 `vi_dispatch_invite` 的最大轮次。
**三轮都没候选的订单从未发出邀约 → 这个值恒为 0** → 每次重新派单都从第 1 档重跑整个阶梯，
把 `DISPATCH_EXPAND` 留痕再写一遍（实测同一订单 4 条，轮次还是 2/3）。
`minutesSinceFirstInvite` 同样基于邀约，为 NULL 导致"派单超时转人工"兜底也不生效。
修法：新增 `DispatchMapper.maxReachedRound` = max(邀约最大轮次, DISPATCH_EXPAND 留痕最大轮次)，
`startRound` 改用它。探针连打 3 次 dispatch-now：扩圈留痕稳定 2 条、轮次仍 2/3。
