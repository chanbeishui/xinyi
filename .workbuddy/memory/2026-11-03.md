## 后台数据权限改为多部门任职（提交 5410e0e）

- 原实现 `DeptScope.scopedDeptId()` 只读 `sys_user.dept_id` 主部门，且只看 `isAdmin()`，
  完全没读 `sys_user_dept` 与角色 `data_scope`。后果：`ry`（主部门 105，角色自定义授权 100/101/105）
  的业务数据全为 0（订单都在 dept 100），而符合规范的应见 33 条。
- 现改为 Spring 组件，委托框架 `IDeptScopeService.resolve(loginUser, permission)`：
  超管或 data_scope=ALL → 返回 null（不限制）；DEPT → 任职部门；DEPT_AND_CHILD → 展开下级；
  CUSTOM → `sys_role_dept`；解析为空直接 403（fail-closed）。
- 两套语义必须分开用，混用会越权或漏数据：
  - `visibleDeptIds()`：列表可见范围（可含下级）→ 订单/车辆/售后/统计/看板
  - `assignedDeptIds()` / `coversAssigned()` / `requireAssigned()`：记录归属是否属于我（精确）
    → 第三方配置详情、线下付款核实
  - `writeDeptId()`：写入用它，请求值必须在任职范围内，未指定落主部门
- Mapper 侧：17 个查询的 `@Param("deptId") Long` 改成 `@Param("deptIds") List<Long>`，
  SQL 由 `dept_id IN (SELECT ... WHERE dept_id = #{deptId} OR FIND_IN_SET(...))` 改为
  `dept_id IN <foreach>`；**展开统一在 Java 做**，SQL 里不再重复相关子查询，保住索引。
  注意 `AdminMapper`/`OrderMapper`/`VehicleMapper` 里的子查询是跨行书写的，批量替换要能容忍换行。
- `IntegrationMapper` 的 15 个 `deptId` 参数**故意保持单值**：路由/档案解析是"某个部门的那条配置"，
  改成集合会改变精确优先、全局兜底的语义。

## 荣利模块分层重构（2026-11-03，9 个提交）

原结构是 `controller/ service/ mapper/` 三个横目录各装 20+ 类，三层切分维度互不一致
（Controller 按 URL 前缀、Service 按功能块、Mapper 按"谁要用"），领域边界在三层错位。
改为 **16 个功能域纵向切分**，每域 `controller/service/mapper/dto` 自成一套：
admin、auth、order、dispatch、fulfill、ledger、payment、aftersale、driver、vehicle、

**规模变化**：90 个类 → 109 个；controller 21→37、service 25→40、mapper 15→24。
`AdminService` 2597→0（拆成 10 个域服务后门面已删）；`AdminMapper` 568→0（拆 5 个）；
`MiscMapper` 54 条 SQL→0（拆 6 个）。URL 全程未变：326 条路由 / 去重 284 条。

### 重构暴露的三个隐藏耦合（静态检查发现不了，只有启动容器才炸）
1. **bean 名冲突**：荣利 `CommonController` 与 RuoYi 自带 `com.xinyi.web.controller.common.CommonController`
   简单类名相同 → bean 名都是 `commonController` → `ConflictingBeanDefinitionException`。
   **这个冲突重构前就潜伏着**，改名 `ViCommonController` 解决（URL `/api/common` 不变）。
   **教训**：新增 Controller 前先查全仓有无同名类（`grep -rn "class Xxx"`）。
2. **`@RestControllerAdvice(basePackages=...)` 是字符串硬编码**：`ViExceptionHandler` 写死
   `"com.xinyi.rongli.controller"`，控制器按域分散后不再匹配 → `ApiException` 落回框架兜底
   → 未登录返回 **500 而非 401**。已改 `"com.xinyi.rongli"`。
   **任何按包名扫描的注解（MapperScan/ComponentScan/RestControllerAdvice）都要在重构时同步核对。**
3. **包级私有方法跨包失效**：`BookingService.releaseReservations` 原本 `void`（包级私有），
   靠"同在 service 包"被 `AfterSaleService` 调用；跨包后必须提为 `public`。

### 必须 clean 打包
`mvn package` 不清 target 时，`target/classes` 里**旧包 class 残留**会与新类同 bean 名冲突
（实测报 `com.xinyi.rongli.controller.admin.AdminFulfillController` 冲突）。
**包结构变更后必须 `mvn clean package`**。

## 后台菜单页 404：路由名跨层级撞名（15:45 修复）

**现象**：`/rongli/inspect/config/wechatPay`（系统设置-微信支付）打开是 RuoYi 404 页，
菜单可点、后端 `getRouters` 也确实返回了该路径，但前端路由表里没有。

**根因**：`SysMenuServiceImpl.getRouteName()` 在 `route_name` 为空时用 **path 首字母大写**兜底，
而 path 只在同一父级下唯一。实际撞了两对：
- `rongli/inspect/config` 与 `system/config` → 都是 `Config`
- `rongli/inspect/config/wechatPay` 与 `rongli/integration/wechatPay` → 都是 `WechatPay`

Vue Router 4 的 `router.addRoute()` 遇到同名路由**先移除已注册的同名记录**，
于是后注册的 `integration/wechatPay` 把 `inspect/config/wechatPay` 顶掉了 → 落到 404 通配。
（与 2026-07-30 那次 `Index` 冲突同一类问题，这次是跨层级。）

**修法（两层）**
1. 数据：`sql/migration_20261103_01_rongli_route_name_unique.sql` 给 2113/2141/2242 显式指定
   `route_name`（`RongliInspectConfig` / `RongliConfigWechatPay` / `RongliIntegrationWechatPay`），
   path 不动、URL 不变；已加入 `docker-compose.yml` initdb 清单（46_route_name_unique.sql）。
   迁移自带自检 SELECT，应返回 0 行。
2. 前端兜底：`store/modules/permission.ts` 新增 `dedupeRouteNames()`，在 `filterAsyncRouter`
   **之前**对三份路由数据各自去重（各自独立跑，结构此时一致才能改出一致的名字；共用一个 Set
   会因 `type=true` 拍平少掉中间节点而产生错位）。重名改 `Name_2` 并 `console.warn`，
   同时把 `constantRoutes` 已占用的名字纳入避让，防住 `Home`/`Data` 这类再犯。
   以后业务在后台加菜单撞名，只是控制台警告，不会再静默 404。

**验证**：`getRouters` 全量无重名；用 vue-router + 真实 getRouters 数据跑
`createRouter/addRoute/resolve`，修复后与「人为还原旧重名数据」两种情况都能匹配到该 URL。
