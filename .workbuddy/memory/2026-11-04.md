## 本次确认的关键坑（部署时必须照做）

1. **profile 顺序必须是 `druid,prod`**：`application-druid.yml` 里是开发库地址
   （localhost:3307 + 本机密码），写成 `prod,druid` 会被后加载的 druid 覆盖回开发库。
   后加载的 profile 优先，这条不写进文档必踩。
2. **`quartz.sql` 必须单独导入**：`ry_20260417.sql` 里 `QRTZ` 出现 0 次，
   根 `docker-compose.yml` 也没挂载它（说明 compose 环境本身缺定时任务表）。
   漏导 → 定时任务模块直接报错。已在手册导入顺序里排第 2。
3. **两个 demo seed 生产禁用**：`seed_20261021_rongli_demo_accounts.sql`（脚本自身写明
   生产不要执行）、`seed_20261022_rongli_reconcile_demo.sql`（支付核对演示数据）。
4. **MySQL 必须 8.0**：基础 SQL 用 `utf8mb4_0900_ai_ci`，5.7 导入即报 Unknown collation。
5. **容器 MySQL 要设 `default-time-zone=+08:00`**：面板默认 UTC，后端连接串是 Asia/Shanghai，
   不一致会出「时间差 8 小时」。
6. **Docker 发布端口绕过 ufw/firewalld**：宿主机防火墙拦不住容器端口，
   最终防线只能是阿里云控制台防火墙不放行 3306/6379。
7. 校验基线：导入完成后 `vi_*` 表应为 **80 张**，`QRTZ%` 表 11 张。

- **境内服务器未备案时 80/443 被拦截** → 过渡用 `IP:8081`；80 打不开不是 Nginx 问题
- **"服务器被微信前端访问"才要备案，"服务器访问微信"不要**：`code2session` 后端出网调用，
  备案前就能验证真实微信登录
- 小程序未备案时**域名加不进 request 白名单**（备案通过后 10 分钟~2 小时生效）；
  备案前只能靠开发版/体验版「不校验合法域名」+ 真机「打开调试」联调
- **微信支付必须等备案**：支付授权目录/回调要求已备案 HTTPS 域名
- 小程序 `API_BASE` 用法是 `${API_BASE}/api/common/...`（`src/utils/request.ts`），
  所以临时期 `VITE_API_BASE=http://IP:8081/prod-api`，少写 `/prod-api` 会全 404
- 小程序 appid `wx22f41349e671b362`；`VITE_LOGIN_MODE=mock|wechat` 与后端 mock 开关必须配对；
  员工关联只能走「微信手机号授权 → 手机号唯一匹配」（V6.4 §2.5）
- 第三方参数在后台「集成配置」按 TEST/LIVE 分槽（`WECHAT_APP`/`WECHAT_PAY`/`TENCENT_SMS`/
  `ALIYUN_SMS`/`PAYMENT_POLICY`），LIVE 槽位空着会按原因码 SKIPPED，不会退回默认通道
- 切换时必须**停用 8081 临时站点并删 .htpasswd**，否则公网明文入口长期存在

## 影像存储迁到对象存储（x-file-storage + 阿里云 OSS，18:20 完成）

**背景**：照片原本落服务器本地磁盘（`~/rongli-uploads`），存在三个硬伤：单盘无冗余、迁移要搬目录、
备份脚本压根没覆盖该目录。用户决定整体切到 OSS 并**不再保留本地磁盘方案**。

**依赖归属（2026-11-04 18:40 纠正：放 common，不放 rongli）**
最初结论是「放 xinyi-rongli、不进 common」，被用户当场质疑「以后代码生成模块要用的时候呢」，
复核后确认原结论错误，已改到 `xinyi-common`。原四条理由的实际检验：
- ❌「扩散到所有模块、撑大包体」：**伪论据**。单体部署所有模块打进同一个 fat jar，
  实测挪位置前后 jar `97545575 → 97545807`，差 232 字节；且 `x-file-storage-spring` 只传递
  `x-file-storage-core`，华为/AWS/腾讯/七牛/GCP/MinIO/Azure 全是 optional，根本不会进来
- ❌「common 是无云厂商语义的工具箱」：common 早就背着 security、redis、poi、yauaa，
  而且 `common/utils/file/FileUploadUtils` 本身就是文件上传工具 —— 上传能力本来就该在这一层
- ⭕「只有一个消费方」：真实，但这是**当下的巧合，不是架构约束**。generator 的可达路径只有
  common（generator → common，不经过 rongli），要用就得反向依赖业务模块，是分层倒置
- ❌「common 没有 @Configuration，注解无处安放」：注解按文档放启动类即可，与依赖归属无关
（`@EnableFileStorage` 仍按文档写在 `RuoYiApplication`，两件事互不影响）
实测 `mvn -o -pl xinyi-generator -am dependency:tree` 可见 generator 已拿到
`x-file-storage-spring:2.3.0` 与 `aliyun-sdk-oss:3.16.1`（compile），可直接注入使用。

**注解按文档放在启动类（2026-11-04 18:30 纠正）**
官方快速入门原文：「在启动类上加上 `@EnableFileStorage` 注解」。**照做**：
`RuoYiApplication` 上加注解，原先自建的 `media/config/MediaStorageConfig` 已删除。
> 我一度把注解放在 rongli 自己的空 `@Configuration` 上，并声称"这是不放 common 能成立的关键"——
> **这个论证是错的**。admin 通过 `xinyi-rongli` 的传递依赖本来就能拿到 `x-file-storage-spring`，
> 注解放哪与"依赖是否进 common"完全无关。技术上 `@EnableXxx` 放任意被扫描的配置类确实等价，
> 但那是实现细节，不是可以偏离文档的理由：多一个只含注解的空类，新人按文档找不到注解，
> 还破坏了项目里 `@EnableScheduling` 等注解统一在启动类的惯例。**能跑通 ≠ 规范。**

**Boot 4.0.6 兼容性（实测通过）**
该库 2.3.0 用 Boot 2.7.2 **provided** 编译，jar 里既无 `AutoConfiguration.imports` 也无
`spring.factories`（全靠 `@Import`），不用 javax。因此 Boot 4 下编译、启动、平台装配都正常，
日志可见 `加载阿里云 OSS 存储平台：aliyun-oss-1`。

**踩坑：读写两条路的 platform 口径不一致（重要）**
`fileInfo.getPlatform()` 在 download/exists/delete 时**直查平台、不回退 default-platform**，
不显式设就报 `没有找到对应的存储平台！platform:null`（HTTP 422）。
default-platform 只在上传的 `of()` 里生效。修法：`vi_file.object_key` 还原 FileInfo 时
`.setPlatform(配置的 default-platform)`，上传也显式设，两条路统一。

**改造范围**
- `MediaService`：删 `Paths/Files/StandardCopyOption`，改 `fileStorageService.of(file)`
  `.setPath(dir).setSaveFilename(name).upload()`；sha256 改为对 `MultipartFile` 流计算；
  `resolveContent(Path)` → `requireReadyFile(Row)` + `assertReadable(Row)` + `writeContent(Row,OutputStream)`
- `access()`：`?token=` 死参数删除，改 OSS **预签名 URL**（之前那个 token 后端从来没校验过）
- `MediaController` / `AdminFulfillController`：改 `void` + `response.getOutputStream()` 流式转发
- `BizConfig.mediaRoot()` 删除；配置项 `rongli.media.root` 作废
- `assertReadable` 先做 HEAD 再写字节：响应一旦开始写就没法再返回 JSON 错误了

**边界（未做，需用户决策）**

- 存量 61 条 `vi_file` + 本机 60 个文件未迁移（本机是演示数据），生产若有真实影像要先传 OSS 再切
- 未端到端验证真实上传/下载：没有 OSS 凭据。用假凭据验证到"平台已装配 + 请求到达 OSS"这一层

**验证**：`mvn clean package` 通过；18080 启动；无凭据时读文件返回 422
