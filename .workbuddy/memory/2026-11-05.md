## 用户文件全部去本地化（commit `3f83050`）

**背景**：影像早已走 OSS，但 RuoYi 自带 `/common/upload`（富文本、头像）、Excel 导入提取的图片、
Excel 导出文件仍写 `ruoyi.profile` 本地目录，是最后一处本地存储。

**改法**：

- 新增 `com.xinyi.common.utils.file.OssFileService`（Spring Bean），统一门面：
  `upload(MultipartFile, dir, allowedExt, uuidName)` / `uploadBytes` / `uploadBytesNamed` /
  `writeTo` / `exists` / `delete` / `presignedUrl` / `keyOf`。
- **ACL 分两类**：通用上传 `public-read`（地址要长期存库、直接喂 `<img src>`，签名会过期，
  头像会天天裂）；业务影像仍是私有对象 + 短链（MediaService 未动）。
- `FileUploadUtils` / `FileUtils` / `ImageUtils` / `ExcelUtil` 都是静态工具类，拿不到注入的
  bean，统一经 `SpringUtils.getBean(OssFileService.class)` 转发，历史调用点零改动。
- Excel 导出改 `ByteArrayOutputStream` 写内存后上传，不再落 download 目录；
  `/common/download`、`/common/download/resource` 改为从 OSS 读流。
  `checkAllowDownload` 要用 `FileUtils.getName(url)` 取最后一段，否则完整 URL 带 query 会被判非法。
- `RuoYiConfig` 删 `profile` 与 `getProfile/getUploadPath/getAvatarPath/getDownloadPath/getImportPath`；
  `application.yml`、`application-prod.yml` 去掉 `ruoyi.profile`；
  `ResourcesConfig` 去掉 `/profile/**` 的 `file:` 目录映射（留着会指向 null）。
- **新增 `/profile/**` 兼容层** `ProfileResourceController`：历史数据里 `/profile/upload/x.png`
  仍能显示，但内容从 OSS 按 key 取。404 用 `setStatus`，不要 `sendError`（会转派 `/error` 变 200+401）。
- 备份脚本去掉 upload 目录打包；部署文档目录规划、验收清单、排障表同步。

**验证**：全量 `mvn compile` + `package` 通过；18080 起实例，`/api/common/session` 401、
`/profile/upload/nope.png` 返回 404（证明新 controller 生效、且不再有本地静态映射）。

**遗留**：生产 Bucket 必须关闭「阻止公共访问」，否则 `public-read` 上传报 AccessDenied。
历史本地文件未迁到 OSS，`/profile/**` 兼容层只能命中已存在的对象。

## 12:30 对象存储命名与目录规范化（commit 16fdbef / a2afaf6）
- 用户说「把问题都改了」，指上一轮我列出的 5 个 key/目录问题 + 2 个次要问题。

改的东西：
1. `upload/` 按业务分三层（rich-text / image / file），前端 `/common/upload?biz=` 声明；
   `OssFileService.dirForBiz` 映射，未知取值落 `upload/`。
2. 业务影像 key 改为 `用途/ord-订单号/yyyy/MM/dd/用途_12位随机串.ext`，订单段排在日期前
   （前缀删除是唯一的批量手段）。
3. 日期统一 `yyyy/MM/dd`（原影像是 `2026-11-05`）。
4. 导出目录 `download/yyyy/MM/dd/`。
5. 上传类型加魔数校验（jpg/png/gif/bmp）。

踩到的坑：
- `FileUploadUtils.logicalDir` 旧实现只取最后一段，`upload/rich-text` 会被压成 `rich-text`。
  改分层前必须先改它，否则表面改了、实际全落根上。
- OSS V1 签名 CanonicalizedResource 必须自己拼 `/<bucket>/?lifecycle`。从请求 URL 截会得到
  `/?lifecycle`（三级域名不含 bucket 段），报 SignatureDoesNotMatch，很容易误判成 SK 错。
- 拿真实凭据跑生命周期 dry-run：签名过了但 `AccessDenied`——RAM 策略只有对象级四条动作，
  缺 Bucket 级 `oss:GetBucketLifecycle`/`PutBucketLifecycle`（Resource 不带 `/*`）。没有擅自 --apply。
- 发现一个事实：后台各模块导出走的是 `exportExcel(HttpServletResponse,...)`，直接写响应流，
  不落 OSS；`download/` 目前实际为空。之前把它当"只增不减"的问题说重了，已在文档与提交里更正。

验证：新增 10 条单测（common 模块为此加了 test 作用域 starter-test），实机 18080 跑通
biz 分层三个前缀、伪装 png 被拒（code=500 后缀不正确）、测试对象已清理。

## 头像回写报 Data too long（14:40 修复）
- 现象：上传头像 HTTP 200、OSS 对象生成成功，但回写用户报
  `Data truncation: Data too long for column 'avatar'`，前端只看到"头像没变"
- 根因：`sys_user.avatar` 是 RuoYi 上游的 varchar(100)，存的是 `/profile/avatar/xxx.png`
  这种三十来字符的相对路径；改存 OSS 直链后实测 **105 字符**，超限
  （`https://rongli-miniwx.oss-cn-shenzhen.aliyuncs.com/avatar/2026/11/05/<32位>.png` 就 105）
- 修法：放宽到 varchar(500)。**为什么仍存直链不存 key**：RuoYi 的 `<img :src="userStore.avatar">`
  直接消费该字段，存相对值会解析到前端域名上；所以列宽必须按直链预算
- 落地：`sql/migration_20261105_01_sys_user_avatar_widen.sql`（幂等 + 自检）
  + `ry_20260417.sql` 同步 500 + docker-compose 挂 52 号
- 教训：**把"存路径"改成"存 URL"时，凡是原先存路径的列都要复核长度**。
  本库只剩 `sys_user.avatar` 一处（`vi_file.object_key` 是 255 且存 key 不存 URL，没问题）
- 顺带修掉一条长期红的 CI 断言：分组可见页面 20→21（2140 业务参数被 20261103_02 挪进巡检组）

## 14:50 头像上传成功后当次裂图（前端拼接口前缀）

- 现象：个人中心上传头像提示「修改成功」，但头像位置仍是破图；**手动刷新网页后正常**。
- 根因：去本地化（3f83050）后 `/system/user/profile/avatar` 返回的 `imgUrl` 从
  `/profile/avatar/xxx.png` 变成 OSS 完整直链。`userAvatar.vue` 仍无条件执行
  `VITE_APP_BASE_API + imgUrl`，拼出 `/dev-apihttps://...` 非法地址；同一坏值还写进
  `userStore.avatar`，连带导航栏、锁屏头像一起裂。刷新后 `getInfo()` 走 `isHttp()` 分支
  直接用直链，所以看起来「刷新就好了」——不是 OSS、不是缓存，是上传回显这一条路径漏改。
- 修法：`isExternal()` 判断，绝对地址直接用，仅历史 `/profile/...` 相对路径才拼前缀；空值兜底。
- 排查中排除的干扰项（别再往这些方向找）：
  - 实库 `admin.avatar` 已是 105 字符直链，列宽已放宽到 `varchar(500)`（e19e621 生效）
  - `curl` 直链 HTTP 200 / `image/png` / 8526 字节，匿名可读，`public-read` 正常
  - OSS 默认域名对图片返回 `Content-Disposition: attachment` + `x-oss-force-download: true`
    （阿里云 0048-00000100，2019-09-23 后建的桶默认行为，要消除须绑自定义域名）。
    无头 Chrome 实测 `<img>` 仍 `naturalWidth=200`，**只影响直接打开链接时的下载，不影响
    `<img>` 渲染**，不是本次头像裂图的原因
- 验证：`npx vite build --outDir dist-verify-20261105-avatar` 通过；三组 URL 断言
  （直链 / 相对 `/profile` / 空值）输出符合预期。
- 遗留：`components/Editor/index.vue:162` 富文本插图同样是无条件
  `VITE_APP_BASE_API + res.fileName`，上传后插图会裂，本次未改（待用户确认）。
- 教训：**后端返回值从「相对路径」升级成「绝对 URL」时，前端所有拼 baseAPI 的消费点都要
  逐个复核**。`ImagePreview` / `ImageUpload` / `store/modules/user.ts` 已用 `isExternal`/`isHttp`
  兼容，漏掉的是 `userAvatar.vue` 和 `Editor/index.vue`。
