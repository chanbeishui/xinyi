## 派单恢复「就近优先、无定位兜底」（commit cceb067 / 39c91c8）
- 上一版把定位从派单里彻底摘掉后，候选顺序退化成纯 id 轮询，近的车不派、远的先派。
- 改为两档：有定位（captured_at 在 locationFreshSeconds 内且坐标可解）按 haversine 距离升序，
  同距按 id 稳定排序；无定位/过期/解不开进兜底队列，按全局游标轮询。
- **游标只在兜底队列推进**；有定位那一档按距离选人。否则「明明有近的却因游标被跳过」。
- `pickCandidate(order, exclude)` 需要 order 的 vehicle_snapshot 取接车坐标。

## 生产库名存在自相矛盾（待确认）
- `deploy/prod/application-prod.yml` 注释写「本环境生产库为 rongli_wx（不是 xinyi）」，
  但同一段的 `url` 仍是 `jdbc:mysql://127.0.0.1:3306/xinyi`。
- `deploy/prod/backup-xinyi.sh` 的 `DB_NAME` 默认 `rongli_wx`。
- 结论：执行任何生产 SQL 前先用 information_schema 确认哪套 schema 里有 `vi_driver_profile`，
  不要照抄库名。两者不一致说明配置或备份脚本有一边是错的。

## 车辆「资料状态」不是审核项，已从后台移除（commit f5d6b31 / f1dfc82）
- 字段是 `vi_vehicle.verification_status`（NOT NULL DEFAULT 'PENDING'），
  **没有任何业务逻辑读它**（下单、派单、检测都不看），只是后台手动标记。
- 唯一修改入口藏在「车辆档案 → 编辑资料 → 资料核验」下拉里，列表上自然没有“审核按钮”，
  所以看上去像流程卡住。线上截图显示「资料待完善」，是旧构建的文案（现源码是「资料待核验」）。
- 真正有业务门槛的是 **行驶证核验** `vi_vehicle_license.review_status`（OrderMapper 会校验），
  在「检测待办」页的「资料待核验」分桶里，两个概念不要混。
- 现在：列表列+筛选+详情三处+编辑下拉全部去掉；「编辑资料」改为「维护备注」，只改 internal_remark；
  车主档案的关联车辆把该标签换成「默认车辆」。
- 后端 `maintainVehicle` 保持「不传 verificationStatus 就取库里原值」；
  留痕原来记请求参数，前端不传会写成字符串 "null"，已改为记实际落库值。
