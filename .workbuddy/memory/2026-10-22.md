## 小程序"登录令牌频繁失效"定位与修复

### 根因（实测确认，非 TTL 问题）
后端 `AuthService` 在 **switchRole / switchStation / consumeBinding(员工绑定)** 里都会
`revokeTokensBySession` 撤销整条旧令牌链并签发新令牌；前端这三处只调 `applySession(view)`
更新内存状态，**从不把返回的新令牌写进 Storage**（`settings/index.vue` 甚至直接丢弃返回值）。
之后所有请求带的是已被服务端撤销的旧令牌 → 401；续期用的 refresh 也在同一次撤销里失效
→ 无法自愈 → `toLogin()` 回登录页。用户体感即"频繁失效"。

### 判定证据（下次直接查这三项）
- `vi_session_token` 中 `consumed_at` 非空 = **0/96**（续期从未成功过一次）
- 每个会话 `generation` 恒为 1（从未发生第 2 代）
- 9 分钟内新建 7 个 session（02:51–03:00）= 反复重新登录，不是续期
- session 85：ctx=1 的令牌对在 `.134` 被撤销、ctx=2 在 `.136` 签发，间隔 2ms = switchRole 的痕迹
- 接口实测：`/api/common/session` 带旧令牌 401、带新令牌 200；旧 refresh 401「已失效」

### 并发漏洞（真实存在）
`refresh()` 里 `consumeToken(...)` 返回值被丢弃，并发两个刷新都能通过 `findToken` 校验，
后到的会执行 `revokeTokensBySession` **把前一个刚签发的新令牌一起撤销** → 令牌失效循环。
修：`if (consumeToken(id) == 0) throw unauthorized("刷新令牌已被使用")`。

### 修复清单
- `store/session.ts`：`applySession` 内 `if (view.accessToken) saveTokens(...)` —— 一处覆盖三调用点；
  `session()` 返回 `sessionView(sessionId, null)` 不含 accessToken，不会误覆盖
- `utils/request.ts`：`RequestOptions.token` 快照；401 时若 `readAccess() !== 快照` 直接重放不刷新；
  `refreshing` 改为结果落地后释放（原 `complete` 同步置空会引发多余轮换）；`toLogin` 加 `redirecting` 闸门；
  `uploadFile` 补 401 刷新重试
- `App.vue`：硬编码 `'rongli_access_token'` 改用 `STORAGE.access`
- `AuthService`：三处 TTL 改 `@Value`（`rongli.auth.access-ttl-minutes:120` 等，默认值不变）
- 新增 `logs/verify_token_refresh.py`（14 项），已并入 `run_acceptance.py` → **126 项全通过**

- 配置页路由：系统设置 → 业务参数 / 微信支付 / 短信通道 / 订阅消息（菜单 2140~2143）

### 本轮修掉的三个真实缺陷（都是被验收逼出来的）
1. **业务错误一律 HTTP 200**：框架 `GlobalExceptionHandler` 优先级高于 `ViExceptionHandler`，
   导致 11 条断言全红、客户端拿不到 401 无法触发令牌续期。
   修法：`ViExceptionHandler` 加 `@Order(HIGHEST_PRECEDENCE)`，错误体同时带 `message` 与 `msg`
2. **售后创建返回管理端视图**：`create()` 里写死 `detail(caseId, true)`，走部门权限校验，
   小程序会话无后台用户上下文 → 数据已入库但回 401。改成按申请人身份选视图口径
3. **订阅配置一关就开不回来**：必填缺失被当硬错误拦保存。拆成
   `formatProblems()`（拦截）/ `problems()`（提示），必填缺失只提示不拦

## 定位「POST /api/app/owner/vehicles 400 车型不在可选范围内」（18:29~18:36）

### 根因（真正卡住用户提交的那一环）
`GET /api/common/dict/vehicle_type` 返回的是
`{"dictType":"vehicle_type","total":5,"items":[{"label":"轿车","value":"sedan"},...]}`，
而 `xinyi-rongli-wx/src/pages/owner/vehicle/edit.vue` 的 `loadDict()` 写的是：

```js
const list = await commonApi.balanceSheet('vehicle_type')
types.value = (list || []).map(d => ({ label: d.dictLabel, value: d.dictValue }))
```

把**对象**当数组 `.map` → 抛 TypeError → 掉进 catch → 兜底成
`[{label:'小型汽车',value:'SMALL_CAR'},{label:'大型汽车',value:'LARGE_CAR'}]`。
页面因此显示「小型汽车」，提交 `SMALL_CAR`；
而 `sys_dict_data` 里 `vehicle_type` 只有 `sedan / suv / mpv / pickup / van`，
`VehicleService.requireVehicleType` 查不到 → 400。

**实测确认**：`SMALL_CAR` → 400「车型不在可选范围内」；`sedan` → 200 建车成功。

### 这就解释了上一轮「提交的数据看不到」
车主侧「新增车辆」是下单前置步骤；车建不出来 → 报价没有车型 → 下单走不通，
所以库里只有脚本（用 sedan）建的车和订单，手动提交一条都没落库。上一轮结论需要修正：
不是"数据在库里只是查不到"，而是**手动提交在第一个写接口就被 400 挡住了**。

### 修复
`loadDict()` 改为兼容 `items / data / rows` 三种包裹 + `label|dictLabel`、`value|dictValue`，
并在末尾 `syncTypeIndex()`；兜底值改为与字典一致的 `sedan/suv/mpv/pickup/van`
（原来那对 `SMALL_CAR/LARGE_CAR` 是"能选中但必被拒"的假选项，报错还会误导）。

### 构建
`dist/dev/mp-weixin`（用户实际在跑这个，16:39 的旧产物）与 `dist/build/mp-weixin`
都已重新生成，`SMALL_CAR` / `小型汽车` 已消失，含 `.items` 解析。
dev 是 watch 模式，`timeout 120` 跑完即被终止，用户需自己重启 `npm run dev:mp-weixin`。

### 教训
- 前后端契约要看**实际响应**，不能只看字段名想当然：本项目里
  `/api/admin/orders` 返回驼峰、`/api/admin/owners` 返回下划线、`/api/common/dict` 又包一层 `items`，三种风格并存。

  排查成本成倍上升。兜底必须与后端约束同源，或干脆不兜底。

## 修复「全系统时间显示错误」（19:00~19:20）

### 根因：同一批接口混着三种时间形状，前端一个都没转
1. `ViTime.iso()` 输出 `2026-10-21T05:00:00.000Z`（UTC 绝对时刻）
2. MyBatis 行对象的裸 `LocalDateTime` 被 Jackson 直出成 `2026-10-21T02:18:02.638`（**没有 Z**），
   浏览器按本地时间解析 → 再差 8 小时，最隐蔽
3. 若依 `BaseEntity` 的 `java.util.Date` + `@JsonFormat` 输出 `2026-10-21 09:13:53`（本地时间，本来就对）

截图那两列就是第 1 种：`05:00:00.000Z` 实际是北京 13:00，`04:30Z` 是 12:30。
库里数据没错，坏的是展示层。

### 另一层：字段名对不上导致整列空白
- 档案类接口（owners / vehicles / ownerOrders / vehicleResults）把 MyBatis Map 原样抛出，
  键是下划线 `pickup_starts_at`，页面读 `pickupStartsAt` → 全空
- 订单/车主订单/车辆订单的「上门时段」绑的是 `pickupWindow`，接口从来没这个字段

### 修复
- 新增 `xinyi-ui/src/utils/datetime.ts`：`formatDateTime`（Z 与裸 ISO 都按 UTC，+08 用
  「先平移再取 UTC 分量」实现，不依赖浏览器时区）+ `normalizeTimeStrings`（递归改写响应体）
- `xinyi-ui/src/utils/request.ts` 成功分支统一调 `normalizeTimeStrings(res.data)`，
  **一处改动覆盖所有页面**；若依的 `yyyy-MM-dd HH:mm:ss`（带空格无 T）原样不动
- `AdminService` 新增 `camelRows/camelRow/enrichOrderRow`：键转驼峰、`LocalDateTime` → `ViTime.iso`，
  并补 `pickupWindowLabel / fulfillmentStatusLabel / totalYuan`
- `ViTime.windowLabel(start,end)`：同日输出 `2026-10-21 13:00 - 15:00`；
  派单队列、订单列表（StationService.listOrders）、车主/车辆订单都带上
- 视图：dispatch/order/owner/vehicle 的时段列改绑 `pickupWindowLabel`
- `ruoyi.ts parseTime`：原来把 `-` 换 `/` 却**保留尾部 Z**（`2026/10/21 05:00:00Z`），
  浏览器解释不一致 → 带偏移的字符串直接交给 `new Date()`
